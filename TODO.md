### Blow mechanic: standalone Rapier prototype (island, gust, recovery, off-edge event)
- **Status**: ✓ Complete 2026-09-19, built from a self-contained spec (`BLOW_SPEC.md`, repo root) rather than an in-conversation request — see that file for the exact decisions this was built to and what's explicitly out of scope (turn logic, multiplayer networking, final art, the Cavern's actual game-over consequence).
- **What it is**: a callable physics module for the "blow another player toward the island's edge" minigame — a flat circular island, one or more player cards, a `blow(handle, { direction, strength })` that gusts a card per `blow-trial.js`'s tuned multi-puff approach, and two distinct outcomes once the physics settles: landed upright somewhere on the island, or went off the edge.
- **Extends `blow-trial.js` rather than rewriting it**, per the spec's instruction to treat its constants/approach as a tuned baseline: `GUST_DURATION_STEPS`, `GUST_PUFF_COUNT`, `PUFF_JITTER_MAG/ANGLE`, `PUFF_SPREAD_X/Y`, `UPRIGHT_SPRING/DAMPING`, `FLUTTER_STRENGTH/MIN_SPEED`, and `BLOW_BASE_SPEED` are all carried over unchanged. The off-centre-impulse-generates-torque-for-free technique (`applyImpulseAtPoint` at a jittered card-local point, not through the centre of mass) is the same trick, just applied per-player instead of to one module-scope card.
- **Why this needed a genuinely different structure from `blow-trial.js`, not just a copy-paste**: `blow-trial.js` is one card, one mouth position, direction always recomputed toward wherever the card currently is, and its DOM element lookups (`document.getElementById('distance')` etc.) live at module scope alongside the physics — fine for a single tuning page, but the spec explicitly asks for "a small, callable API rather than a page that only works via its own UI" and for direction to be an explicit caller-supplied parameter, not derived from blower/target positions. So `blow-arena.js` exports pure functions (`createArena`, `addPlayer`, `blow`, `step`, `getPlayerState`) with **no DOM references at all** — it runs unmodified in a headless Node script with no `document` (see Testing below) — and a separate `blow-arena-demo.js` does the DOM wiring for the actual page, importing the module rather than being part of it. `blow-trial.js` itself is untouched.
- **Island collider is a cylinder, not blow-trial.js's box approximation.** `blow-trial.js` approximated its round island with an inset box collider because nothing depended on the exact edge — the camera just needed a plausible platform to stand on. Here, "off the edge" is a first-class result the caller depends on (`onWentOffEdge`/the rejected-outcome branch of `blow()`'s promise), so the physical support has to disappear at exactly the radius the game logic checks against. `RAPIER.ColliderDesc.cylinder(halfHeight, radius)` matches the visual deck exactly, so a card that's visibly past the edge has also lost its footing, not still resting on an invisible box corner.
- **Off-edge detection is a straight horizontal-distance check** (`hypot(x, z) > islandRadius` on the card's own translation), run unconditionally every physics step for every player, not just while a blow is "in flight" — per the spec's "at any point after a blow", not only during the gust itself. Once true it's sticky (`player.offEdge`); the card is left to keep falling under ordinary gravity (there's no floor there to catch it, so no further code needs to do anything) and no more outcome/recovery logic runs for that player.
- **Landing/recovery**: at-rest detection is velocity-below-threshold (`REST_LINEAR_THRESHOLD`/`REST_ANGULAR_THRESHOLD`) held for `REST_HOLD_TIME` — same idea the spec pointed at ("same 'at rest' detection idea blow-trial.js likely already needs"), except blow-trial.js never actually needed to *act* on it (a human just watches the card settle), so these three numbers and the upright-tolerance angle (`UPRIGHT_DOT_TOLERANCE`, 20°) are new and are a first-pass judgment call, not read off anything upstream — worth re-tuning once this is watched against a real blow in the real game rather than just this prototype's sliders.
- **Recovery is a kinematic snap, not the upright spring finishing the job.** The upright spring (carried over from `blow-trial.js`) is deliberately weak — strong enough to stop a card from spontaneously toppling at idle, easily overpowered by anything real — so it cannot be relied on to *guarantee* a card ends up upright in a bounded time, which is what the spec asks for ("by the time the blow sequence reports itself finished, the target is guaranteed upright"). Instead, once at-rest-but-not-upright is detected, the card's Rapier body is switched to `KinematicPositionBased` for `RECOVERY_DURATION` (0.45s) and its position/rotation are driven directly (smoothstep-eased lerp/slerp from wherever it landed to standing upright in the same spot), then switched back to `Dynamic` with zeroed velocities. Guarantees both the outcome and the timing, which forces alone don't.
- **Judgment call, flagged per the spec's own instruction to leave a note rather than guess silently**: recovery preserves the card's yaw (which way it was facing horizontally when it settled) rather than resetting to a fixed heading — "stand back up facing however you happened to land" reads more natural than snapping to face some default direction, but the spec doesn't say either way. Comment at `startRecovery()` in `blow-arena.js`.
- **Judgment call**: `blow(handle, { direction, strength })`'s `direction` accepts either a unit vector `{x, z}` or an angle in radians (0 = +Z) — the spec says "unit vector, or angle" without picking one, so both are supported rather than forcing a choice on the caller.
- **The central object is exactly the placeholder the spec assumed**: a static cylinder, decorative only, no special blow-physics interaction (a blow doesn't bounce off it, cards can rest against it same as any other collider). Flagged in both the spec and in `createArena()`'s comment, since the real win-condition/central-object behaviour is separate, out-of-scope work.
- **Files**: [prototype-threejs/src/blow-arena.js](prototype-threejs/src/blow-arena.js) — the callable API (`createArena`, `addPlayer`, `blow`, `step`, `getPlayerState`, `getArenaRadius`, `startLoop`), no DOM dependency; [prototype-threejs/src/blow-arena-demo.js](prototype-threejs/src/blow-arena-demo.js) — UI wiring only, imports the module above; [prototype-threejs/blow-arena.html](prototype-threejs/blow-arena.html) — sliders for add-player distance/angle, blow direction/strength, a target picker (multiple cards, unlike `blow-trial.html`'s one), and a scrolling event log (shows `landed at (x, z)` vs `WENT OFF THE EDGE` vs the raw `onWentOffEdge` firing, so the two outcomes are visibly distinguishable exactly as the spec asks). Local URL once `npm run dev --prefix prototype-threejs` is running: `http://localhost:5180/blow-arena.html`.
- **Testing**: this environment's real-time browser testing has been unreliable for anything that needs to watch a multi-second physics sequence settle (see the fork-branches entry above for the same problem elsewhere in this project) — compounded here by `preview_start` in this particular session insisting on reusing/relaunching the `app` dev server (port 5181) regardless of which `launch.json` config name was requested, so the arena page itself was not watched render in this session's browser pane. Verified instead with [prototype-threejs/test-blow-arena.mjs](prototype-threejs/test-blow-arena.mjs), a headless Node script exercising the real Rapier physics through the real module (no mocking — `createArena`/`addPlayer` just skip their `if (scene)`/`if (document)` branches when there's no DOM) against three cases: a gentle blow near the centre (landed upright, stayed on the island), a full-strength blow aimed radially outward on a card already near the edge (fired `onWentOffEdge` and resolved `{ status: 'offEdge' }`), and a moderate blow (visibly triggered the recovery path — logged "settled non-upright" before resolving landed-upright). All three behaved as expected; rerunning shows the same qualitative outcomes each time (puff jitter varies the exact landing coordinates, not the pass/fail shape). `npm run build --prefix prototype-threejs` was not used to verify this (it currently fails on a pre-existing, unrelated `multiplayer-config.js` missing-file error in `main.js`, present before this change); `node --check` on both new files passed, and the Node run above exercises real module resolution through `node_modules` regardless.
- **Not done, left for later integration per the spec's own scope line**: which device is authoritative for a blow's physics outcome — the spec's own text points toward "the player being blown computes and reports the outcome" as the likely shape (matching `useLobby.js`'s `abduct-target`/`abduct-result` precedent) but says explicitly that wiring is a separate, later pass, so nothing here assumes or half-builds a networking layer.

### Camera facing: still skewed on arrival after the first fix, root cause was upstream of arrival
- **Status**: ✓ Complete 2026-08-28. Two fixes, the first incomplete.
- **The report**: after arriving at a new island, the camera stayed pointed the direction the player had been walking rather than resetting toward the temple.
- **First fix (incomplete): eased `facing` toward the temple once a leg finishes.** `facing` (the camera's smoothed heading) is only updated by the walking block while a leg is active — the instant the queue empties it just stops being touched, freezing wherever the branch's last waypoint happened to point. Added an else-branch: once there's no leg (and the player isn't falling or finished), ease `facing` toward `sections[forkIndex-1].fork.heading` over ~0.2s (`dt × 20` vs the walking case's `dt × 2.5`). Verified this branch itself works — `facing` reliably reaches the target within a handful of frames once it runs.
- **Luke reported it was "better now, but the angle is still skewed" — the reset was firing, but too late to matter.** Traced a live walk frame-by-frame (driving `window.__tick()` manually rather than relying on this environment's throttled real-time `requestAnimationFrame` — see the falling-mechanic entry's Testing note) and found `facing` reaching **-27°** in the single frame *before* arrival, not some residual drift. That's real, not a bug in isolation: the last waypoint of any branch that leads to a real island is always that island's centre (`genForkCurve`'s mirrored-arrival case), reached by one final straight hop in from the arrival edge — and that hop cuts laterally back to the centreline, giving it a genuinely steep heading (~30° at current geometry) compared to the approach as a whole. The walking block was correctly "chasing the direction of travel", as designed — it's just that the direction of travel for that last ~3.5 units is sharply not-forward. The at-rest fix only straightens things out *after* the walk stops, which reads as a last-second snap followed by a correction, not as one smooth turn.
- **Second fix: stop chasing that final hop's literal direction.** Once `leg.queue.length === 1` and `leg.arriveFork` is set (i.e. the only waypoint left is a real island's centre), the walking-facing block now steers toward that destination's already-known heading (`sections[leg.arriveFork - 1].fork.heading`) instead of `atan2(dx, -dz)` to it — the same value the at-rest fix settles on, just applied for the ~0.85s of the final hop instead of only after stopping. Falls back to the literal direction otherwise (a wrong branch's truncated end, or the straight-line intro trunk / temple approach, neither of which has a sharp final kink to correct for).
- **Verified by re-running the same frame-by-frame trace**: `facing` now reaches **0.009 rad (~0.5°)** in the frame *before* arrival, versus -0.47 rad before this fix, while the swing through the *middle* of the curve (up to ~28°, while genuinely following the bow/pinch) is untouched — the fix is specific to the final approach, not a general dampening.

### Fork islands: procedural 3D rock, replacing the shelved billboard
- **Status**: ✓ Live in the game, 2026-08-27. Supersedes the billboard version below, which is no longer wired in — its code is gone from skyPath.js but the description is kept here for the reasoning, and it's still recoverable via git history (commit `417127b` and the one after).
- **Why the billboard was dropped**: it hit exactly the two limits its own write-up predicted — the flatness problem has a hard ceiling (see below), and its pillars/edges couldn't track a fork's actual branch angles. Real geometry sidesteps both: nothing to billboard, nothing that needs to face a particular direction.
- **What it is**: A procedurally generated rock — no art asset, no textures, geometry and vertex colour only. [app/src/skypath/islandGen.js](app/src/skypath/islandGen.js) is a shared module: a `LatheGeometry` profile (wide flat top tapering to a rough base) gives the floating-island silhouette almost for free, then every vertex is displaced by fractal value noise — light near the deck so it stays flat and walkable, heavy toward the base so the underside reads as broken rock. The top is capped with a separate paved disc, and grass tufts are scattered as instanced cones around the rim.
- **Faceted, not smooth**: the mesh is rebuilt non-indexed and its normals recomputed *after* that, so every triangle gets its own flat face normal instead of a smoothed one. At this polycount, smooth shading reads as wet clay; flat faces read as rock immediately. This was the single change that fixed the prototype's first (smooth) attempt.
- **Unlit by design, not by accident**: the first in-game test rendered the rock almost pure black. Cause: every other prop in this game (temple, figure, pavers aside) is `MeshBasicMaterial` with its shading painted into the art — real-time lighting was only ever tuned for shadow-casting, never for making a lit surface look good from a low, close camera. The standalone tuning page's free-orbiting camera sees mostly the top-facing deck and rim, which happened to be well-lit; the in-game camera sits low and close and mostly sees the rock's near-vertical outward faces at a grazing angle to the overhead key light, which read as black. Fix: bake a fixed fake sun into the vertex colours (half-lambert term against each face's normal, floored well above zero so nothing ever goes fully black) and render the rock, deck and grass all unlit (`MeshBasicMaterial`). This is more correct for this codebase, not a workaround — it means the island looks the same at every camera angle and every time of day, same as everything else in the scene, instead of drifting with the sun the way the one lit prop in an otherwise-unlit scene otherwise would.
- **Parameters found on the tuning page, then rescaled for the game's camera**: `bump: 0.32, taper: 0.75, depth: 0.43, size: 14, grassCount: 39` were the values chosen by eye on `island-proto.html`, whose camera orbits freely at ~14 units out. Dropped straight into the game at that size, the island filled the entire screen — the in-game camera rides close behind the walker, so the same absolute size reads completely differently. Halved to `size: 7` (matching the width the old billboard used against this same path, which read correctly) with every other parameter unchanged, since they're all either ratios of size or absolute counts.
- **Per-fork variety comes free**: `spawnIsland()` draws a fresh random seed each time rather than picking from a small fixed set of pre-made images, so no two forks' islands are identical — a better version of the "several images, one picked at random" plan the billboard approach would have needed multiple hand-made assets for.
- **The gap and heading problems from the billboard write-up are gone, not solved**: real geometry has no "facing" to conflict with a fork's branch angles, and there's no card edge to be seen edge-on. The visible gap between the island's edge and the path stones is still there — joining the path properly to the deck edge remains a separate, undone job — but it's no longer compounded by a flatness problem underneath it.
- **A base 3D model can replace this at any time**: `spawnIsland()` is the only place that calls `buildIsland()`; swapping in a loaded `.glb` (hand-modelled in Blender, or from any other pipeline) means changing what that one function returns, nothing else. See the next entry for exporting a shape from this generator into Blender as a starting point.
- **Files**: [app/src/skypath/islandGen.js](app/src/skypath/islandGen.js) — the generator, shared with the tuning page; [app/src/skypath/skyPath.js](app/src/skypath/skyPath.js) — `ISLAND_PARAMS`, `spawnIsland()`, `registerIsland()`, `nearIsland()`, `ISLAND_CLEAR_R`, `ISLAND_Y`; `clearJourney()` disposes each island group's children; tuner has a live `island Y` slider only (shape params need a full mesh rebuild, so they stay on the tuning page, not the live tuner).

### Scale rework, steps 1–3: measurement fix, island-first spacing, character/pacing
- **Status**: ✓ Complete 2026-08-27. Step 4 (converging branches) is also done — see "Fork branches: both routes lead to the same island" below. 3D stones remain — see its own Pending entry.
- **Step 2 — path spacing now derives from the island, not the other way round.** New master constants near the top of [skyPath.js](app/src/skypath/skyPath.js): `ISLAND_RADIUS = 6` and `ISLAND_PATH_GAP = 8` (the one real pacing knob) combine as `FORK_DISTANCE = 2×ISLAND_RADIUS + ISLAND_PATH_GAP = 20`. `TEMPLE_DISTANCE` is now a *result* of `N_FORKS × FORK_DISTANCE`, not an input. `ISLAND_TARGET_RADIUS` and the procedural fallback's own size both read from `ISLAND_RADIUS` directly, so a fallback island (see the loading-race entry above) can never again mismatch a loaded model's footprint.
  - `CURTAIN_DIST` was quietly broken by the same root cause: at `BRANCH_LEN × 0.4` it landed inside the island's deck (a fraction of *path* length has no reason to relate to *island* size). Now `ISLAND_RADIUS + 1.5`, guaranteed to clear the edge.
  - `WRONG_STUB_LEN` now reads `CURTAIN_DIST + 2` rather than its own independent fraction of `BRANCH_LEN` — one dependency chain instead of two numbers that only used to agree by coincidence.
  - Checked and found *not* to need changes: fog radii (about corridor width, not position along the path), cloud row recycling (tiles on camera position, not tied to journey length), bird distances, camera near/far planes. Re-checking and finding nothing wrong is still the point of re-checking — these aren't unexamined.
- **Step 3 — character shrink, faster walk, flatter camera.** `FIGURE_H` scales by a new `FIGURE_SCALE = 0.72` (2.2×0.8×0.72 ≈ 1.27, down from 1.76); `WALK_BOB_HEIGHT`/`WALK_BOB_LATERAL`/`CARD_THICK` scale with it since they're figure-relative *distances* — `WALK_BOB_TILT` (an angle) and `WALK_BOB_RATE` (a cadence) don't. `WALK_SPEED` raised 3.2 → 4.0. Camera pitch lowered instead of pulling `CAM_BACK` in, per the plan: new named constants `CAM_HEIGHT` (3.9 → 2.8) and `CAM_LOOK_Y` (1.25 → 0.9), replacing two bare literals that were previously tuned against the taller figure. Confirmed visually: the character reads noticeably smaller against the island, and the flatter pitch shows more horizon and more of the island's underside, both reading as "bigger world."
  - **Stone size — corrected twice, second time by Luke.** First pass reasoned stones should shrink with the character ("the world feels big because the character shrank inside it, so everything relative to the world stays put"). Luke corrected this: the intent is the *world* being large relative to a normal person, not the person shrinking inside a normal-sized world — so a stone must keep its proportion to the character, and it is the island/path (genuinely huge) that should not carry the character's scale factor. `FIGURE_SCALE` moved up to the shared world-scale block specifically so it can be applied to both the figure and anything sized *relative to the figure* — `STONE_SIZE` now reads `1.0 * FIGURE_SCALE`, and `ROW_SPACING` (already derived from `STONE_SIZE`) follows automatically.
  - **Camera numbers are a first pass**, flagged as such in the code — genuinely a "tune by eye" parameter, worth revisiting after a live playtest rather than treating as final.
- **Two backdrop bugs surfaced by the longer journey, both found and fixed 2026-08-27** (Luke noticed the symptoms; root causes below):
  - **`peaksBand` and `horizonBank` were never parented to `backdropRig`.** Every other backdrop layer (`landSea`, `sky`, the wind-cloud sheets) rides the camera-following rig — see the backdrop rebuild entry below — so it always sits the same apparent distance away regardless of how far the player has walked. These two were fixed at an absolute world Z (−118 and −100) instead, which was invisible as a bug for as long as the journey never reached that far. Once step 2 pushed `TEMPLE_DISTANCE` out to 160, the player's own path now passes *through* those fixed Z positions partway to the temple — walking into a stationary translucent panel that was meant to be permanently-distant scenery is exactly the "grey area that appears then disappears" Luke reported. `horizonBank` is currently `.visible = false` (a legacy layer, off since 2026-08-26) so in practice only `peaksBand` was ever the visible culprit; both were fixed on the same principle regardless, since the same bug would have resurfaced the moment anyone re-enabled `horizonBank`. Fix: both now take `parent: backdropRig`.
  - **`TEMPLE_H` was a fixed absolute size, tuned by eye against the old fixed `TEMPLE_DISTANCE` (70) — nothing recalculated it when step 2 made that distance a derived value.** Apparent (angular) size is physical size ÷ distance; `TEMPLE_DISTANCE` growing to 160 with `TEMPLE_H` unchanged put the temple at under half its tuned apparent size. A billboard that much smaller on screen resolves far less of its own texture detail, which reads flatter and more "cartoonish" — this is almost certainly Luke's "background sky looks too zoomed in and less detailed" report; the flatter camera pitch from the step-3 change (more sky visible in frame) likely made a temple that had quietly become tiny even more noticeable by contrast. Fix: `TEMPLE_DISTANCE_REF = 70` records the distance `TEMPLE_H` was actually tuned against, and `TEMPLE_H` now scales by `TEMPLE_DISTANCE / TEMPLE_DISTANCE_REF` — so it stays correctly sized however `TEMPLE_DISTANCE` is derived from here on, the same fix pattern as `ISLAND_CLEAR_R`/`WRONG_STUB_LEN` above. Confirmed visually: the temple went from a small, flat, distant shape back to filling a large, detailed portion of the frame at the first fork.
  - **Lesson**: this is the second and third time in one day a fixed number silently assumed one particular distance/scale and broke when that distance became derived (`CURTAIN_DIST`/`WRONG_STUB_LEN` were the first). Worth treating as a pattern: when a constant is `X`, always ask what it was tuned *against*, and whether that thing is still fixed.

### Fork branches: both routes lead to the same island (Option B, Step 4)
- **Status**: ✓ Complete, first pass 2026-08-27, corrected 2026-08-28 after Luke's feedback on both passes. Depended on the world scale rework above (steps 1–3), since converging branches only work with a deterministic island position to converge on.
- **What changed**: each branch used to be a straight line from the fork at `cursor.heading ± FORK_HALF_ANGLE` — the correct one running the full `BRANCH_LEN` to feed the next fork's cursor, the wrong one a short separate stub (`WRONG_STUB_LEN`) that simply stopped in mid-air. Now both branches are curves (`genForkCurve()`) that leave the fork at the same ±12° as before — straight, out to the island's edge, so the deck and its pillars need no changes — then bow and curve onward, converging exactly on the same next island. Which side is correct no longer decides where the next island sits, only whether that side's own branch actually reaches it.
- **First pass converged the two branches onto a single bare point, not the island itself — Luke caught this 2026-08-28.** The initial version had both branches bow inward and merge into one line partway there, with a separate straight "trunk" (leftover from the old per-round pacing shape, `TRUNK_LEN`/`TRUNK_SEGMENTS`) carrying that single merged line the rest of the way to the real next island. That put the merge in open air, well short of the destination — "the two paths becoming one path before they get to the island." **Fix**: arrival now mirrors departure. Each branch runs the fork's *entire* `FORK_DISTANCE` span itself (not a shorter branch-only distance, with the trunk making up the rest) and, rather than converging on the next island's centre directly, curves to the *matching* edge point of that island — mirrored off its own heading the same way departure was — and only then takes one final straight step onto the centre. The two lines now stay visibly separate all the way to the destination island's edge and only join on its own deck, exactly mirroring how they only separated on the deck of the island they left. There is no separate trunk phase for forks any more; `TRUNK_LEN`/`TRUNK_SEGMENTS` remain, used only for the intro walk from spawn to fork 1 (which has nothing to mirror, there being no fork there).
  - **Getting the mirror backwards was the first bug inside the fix.** The natural-looking `advance(target, target.heading + offset, +ISLAND_RADIUS)` for the arrival edge places it *beyond* the island, in the direction of travel — the same formula as departure, but departure's edge is correctly *ahead* of its island while arrival's edge needs to be *behind* its island (nearer the fork, since the branch reaches the edge first and only then walks in to the centre). Caught immediately by a standalone reproduction of the curve math outside the game (see Testing below), which showed the "mirrored" branch coming out *longer* than the un-mirrored original rather than the same length with a different shape — advance()-ing *backward* (`-ISLAND_RADIUS`) fixed it.
  - **Removing the trunk phase changes pacing math that quietly assumed it existed**, addressed the same day: `buildFork()`'s `target` is now always `FORK_DISTANCE` forward (previously a shorter branch-only distance, with `TRUNK_LEN` making up the remainder) for *every* fork including the last, even though the last fork's `target` isn't a real island — this keeps `CRUISE_DISTANCE = N_FORKS × FORK_DISTANCE` accurate regardless of which fork is last; only the curve *shape* differs there (see below), not its forward reach.
  - **The last fork has no next island to mirror into**, so its curve shape stays the pre-mirror single-point convergence — `genForkCurve()` takes a `mirrorArrival` flag (false only there) that picks between "curve to the matching edge of `target`, then step onto its centre" and "curve straight to `target` itself." Both shapes share one `genBowPoints()` helper for the actual bow, so there's one bow formula, not two.
- **The wrong branch is the same curve, cut short, not a different shape.** `truncateAtFraction()` walks the curve's own real length (not an assumed one) and returns a prefix stopping at a given fraction of it. Stones are laid up to `WRONG_GAP_FRACTION`; the walkable queue continues slightly further, to `WRONG_FALL_FRACTION` — the existing "leg's queue runs out → `startFall()`" logic (see the anti-cheat entry below) fires there unchanged, so the last stride is onto bare air inside the fog rather than a wall stopping dead at the last stone. No physics raycast needed, same reasoning as the fix this replaces.
- **Fractions ended up back at the original 60–70% guess, once the branch covered the right distance.** The first pass's shorter branch put the fog curtain at ~70% along it, forcing the gap fractions out to 0.82/0.9 to stay past the fog at all. With the branch now covering the full `FORK_DISTANCE`, the curtain falls back to ~40% along it and the mirrored arrival edge to ~70% — so `WRONG_GAP_FRACTION = 0.6` / `WRONG_FALL_FRACTION = 0.68` sit exactly in the open-air gap between those two landmarks: comfortably past the curtain, comfortably short of the island. Verified with the same standalone reproduction (see Testing).
- **The bow direction was backwards, and underneath it the branches were crossing.** Three separate faults, found in that order over 2026-08-28:
  1. **Direction.** `FORK_BOW_WIDTH` shipped at `ISLAND_RADIUS × 0.35` — a lens/eye shape bowing *away* from the other branch, wide in the middle; cut to `× 0.12` after Luke's first sketch asked for something gentler. A second, clearer illustration showed the target shape was the opposite: an hourglass, pinching *toward* the other branch at the midpoint, never touching, then flaring back out. Renamed to `FORK_PINCH_WIDTH` and flipped the sign in `genBowPoints()` rather than just relabelling.
  2. **The branches crossed over — the real fault, and the one that made every version look like it "converged too early".** `advance(target, target.heading + sideSign × FORK_HALF_ANGLE, -ISLAND_RADIUS)` was used to put the arrival edge on the island's near side. A negative distance through `advance()` negates **both** components, forward *and* lateral — so every branch arrived on the *opposite* side from the one it departed on. The two branches formed an X and genuinely met at the midpoint. ### Hand-modelled island, its deck texture, and the √2 measurement bug
- **Status**: ✓ Complete 2026-08-27. Islands now ship as a hand-modelled `.glb` (Blender, started from an `islandGen.js` export) with a real cobblestone deck texture, replacing the fully procedural rock.
- **Loading**: `ISLAND_MODELS` in [app/src/skypath/skyPath.js](app/src/skypath/skyPath.js) lists model + deck texture pairs, loaded via `GLTFLoader` on the shared `LoadingManager`. Add a row per variant; `spawnIsland()` picks one at random per fork.
- **The first island always used the procedural fallback, guaranteed — not a race.** `startJourney()` runs synchronously at mount, before any network fetch can possibly resolve, so fork 1's island was *always* built from `buildIsland()`. Fixed with `upgradeFallbackIslands()`, which swaps a real model into any island still on the fallback the moment one loads, in place — contents change, position and all bookkeeping keyed to it do not.
- **Cloned islands share GPU resources.** `Object3D.clone()` copies geometry/material *references*. Disposing a template-sourced island's meshes in `clearJourney()` would break every other island built from that template, including in the next round — so template-sourced islands dispose nothing, and only a procedural-fallback island (which owns everything it has) disposes normally.
- **Do not find the deck by node name.** Blender's exporter has changed what gets split into which named node on every version of this model so far, including merging the deck into the rock's mesh object. What is stable is the *shape*: the deck is the flattest mesh in the file (near-zero vertical extent). v1's `getObjectByName('Mesh_1')` would have crashed outright on v2.
- **The √2 bug — worth understanding, because it silently invalidated every derived number.** Deck radius was measured as `Box3.setFromObject(...).getBoundingSphere(...).radius`. Three.js builds that sphere from the box's **half-diagonal**; the box around a flat disc is a square, so it reports `r × √2`. A disc of true radius 7.66 measured as 10.84, and the island was scaled by `6 / 10.84` — leaving every island at **1/√2 (71%) of its intended size** while the code went on believing it had got the 6 it asked for. Everything derived from that number inherited the error: `ISLAND_CLEAR_R` suppressed stones out to 6 while the real walkable edge was at 4.24, which is precisely the 1.76-unit stretch of nothing Luke was walking across. Now measured directly off the deck's vertices as max `hypot(x, z)` through the mesh's own world matrix — which is both exact and says what it actually means (*horizontal* reach), and is robust to an off-centre or separately-translated deck.
- **Lesson worth keeping**: a bounding *volume* is not a measurement. When a number is going to be the base unit other geometry derives from, measure the thing itself.

### Backdrop rebuilt: land/sea deck, curved sky, and two-layer wind cloud
- **Status**: ✓ Complete, values baked 2026-08-26. Tuning panel retained but no longer mounted.
- **What changed and why**: the old backdrop was a stack of flat vertical panels (sky strip, sea band, land deck) layered by `renderOrder`. Every problem it produced traced back to the same two mistakes — treating a spatial arrangement as a paint order, and sizing panels to exactly fill the frame. It is now built the way the world actually is, and sized with margin.
  - **Land and sea are one flat deck** (`landsea.jpg`, 4000x4000, square and kept square) lying on a floor at `FLOOR_Y = -40`, running from behind the camera out to `HORIZON_Z = -360`. The coastline is painted into the art rather than being a seam between two planes, which removed the entire class of gap-at-the-join problem the split version kept producing. `deck()` lays the plane so the top of the image ends up at the far edge, which puts the open sea at the horizon and the fields underfoot with no flipping. Mirror-tiled 4x across (`MirroredRepeatWrapping`) so each copy meets its own reflection and there is no seam — that is what lets it run wider than the frame.
  - **The sky is a curved shell**, not a panel (`skyShell()`, a 160° section of a cylinder at radius 400). A flat panel's angular width is `2*atan(w/2d)`, so widening the view means either bringing it closer (which crops it vertically) or stretching it — and either way its vertical edges swing into frame as soon as the camera pans, which is what was being seen. Bending the same strip is strictly better value: it covers `arcLength/radius` radians instead. Kept a section rather than a full ring because only a third of the day-cycle strip is visible at a time, so wrapping it 360° would smear that third over four times the angle. Height is derived, not chosen: `arcLength / SKY_ASPECT` keeps the visible third's own 4:3 ratio so the curve does not distort the art.
  - **Both live in a camera-following rig** (`backdropRig`, tracks camera x/z each frame — no y, no rotation). Fixed in world space they slide past, since six forks is over 100 units of travel, and the horizon climbs the screen over the course of a round.
- **Two bugs found along the way, both invisible in code and obvious on screen**:
  - **The camera's far plane was 400.** The old land deck sat at z=-600 spanning to -1600, so most of it was being clipped: the "edge of the land" being tuned against was the far plane, not the plane's own edge. Worse, the far plane clips at constant *view-space* depth, so an axis-aligned backdrop meets it at an angle once the camera yaws — the panel gets sliced along a diagonal that sweeps across it as the camera turns, which is what "it disappears from one corner depending on facing" was. Now `near 0.5 / far 5000`. `near` was raised alongside because depth precision goes as the near/far ratio and `near` is by far the stronger term, which buys back most of what the longer far plane costs; nothing in the scene comes within half a unit of the camera.
  - **A layer sized to exactly fill the frame shows its edge the moment anything moves.** Everything is now sized with real margin beyond the view.
- **Look-around widened** from ±2.2 to `LOOK_X_LIMIT = 6.9`. Worth recording what this control actually is, because it is not a yaw: it slides the camera sideways while it keeps looking 4.6 ahead of the walker from 7.3 behind, so an offset of L swings the view by `atan(L / 11.9)` — about 10° each way before, about 30° now.
- **Wind clouds** (`windLayer()`): two sheets of cloud below the path blowing right-to-left, the upper lighter one at roughly 3x the speed of the denser one, which is what sells them as two altitudes rather than one texture with a pattern in it.
  - **"Tiled to infinity" is two tricks together**: the sheets sit in the camera-following rig so they can never be walked off, and their UV offsets are driven from the camera's own position, which cancels that following exactly. The texture is therefore pinned to the world — full parallax as the walker moves — on a mesh that is always underneath the viewer. Wind is one extra term added to the same offset, which is why it composes for free.
  - **Direction, derived once and written into the comment** so it never has to be re-derived: `deck()` maps local +x to world +x; raising `offset.x` drags the image toward -x; the player faces -z so their right hand is +x; therefore a rising `offset.x` is right-to-left across their view.
  - **Neither cloud image tiles seamlessly** — each is a single ragged patch with transparent margins — so one sheet repeats as an obvious grid of gaps. Each layer is built from **three passes at ratios 1 : 1.47 : 4.3**, so one pass's gaps fall on another's cloud. The 4.3x pass is the one that does the real work against uniformity: at ~260 units per tile it is *composition* rather than texture, thickening whole regions and opening whole clearings. It uses the *other* layer's art (`swap`) so the big shapes do not echo the small ones. The middle pass is mirrored via a negative repeat.
  - **Gaps**: a shared grid of soft holes punched through every pass of a layer by a small `onBeforeCompile` injection. Two things make it work that a naive "drop every Nth tile" would not — the grid is *shared* across passes (per-pass holes would need `(1/N)^3` coincidence to open a real gap, giving thinning rather than gaps), and the hole is a jittered blob *inside* its cell rather than the cell itself (clearing a whole cell leaves hard straight edges, which reads worse than the uniformity it was meant to fix).
  - **Running-bond stagger**: every other row of tiles shifted half a tile sideways, so vertical seams never line up into a continuous column. This is the one thing the passes-at-different-scales trick cannot do, since a UV transform is affine and a stagger is not. It replaces the map lookup rather than pre-multiplying the UV, because `vMapUv` is a fragment input and therefore read-only.
- **Three shader gotchas worth not re-learning**:
  - **`textureGrad` with the *unstaggered* derivatives is mandatory.** `uv.x` jumps half a tile at each row boundary, so the implicit derivative spikes there and the GPU drops to the coarsest mip — a blurred line along *every* row, a worse artifact than the grid being removed.  Guarded on `__VERSION__ >= 300` so the material still compiles if three ever emits GLSL ES 1.00 here.
  - **`customProgramCacheKey` must be set on any `onBeforeCompile` material.** Three's default program cache key ignores `onBeforeCompile`, so without it an ordinary `MeshBasicMaterial` can be handed the patched program, or vice versa.
  - **The cell hash is the sine-free integer hash**, not `fract(sin(...))`. The cell coordinate grows without bound as the wind blows, and a sine hash bands badly once its input gets large — it would have looked correct for the first minute and then developed stripes.
- **Older ambient cloud layers**, settled by eye rather than derived: `horizonBank` **off** (its job was hiding where the old decks ran out, and the land/sea deck now reaches the horizon on its own), `deckDeep` and `deckHigh` **on** (they read as distant cloud far below the wind sheets), the four recycling `cloudRows` **off** (they occupied the same band the wind sheets now own and doubled up). The fork curtains are untouched — those are gameplay, not weather.

### Path generation: build one fork at a time (anti-cheat)
- **Status**: ✓ Complete
- **Why (the real reason)**: this was previously filed as a memory/replay cleanup, but the actual motivation is **fairness**. Because only the *correct* branch of a fork feeds the cursor the next fork is planted from, the world-position of a downstream fork's pillars encodes which side was correct upstream of it. With the whole route present from the start, a player could read the shape of the path, the angle it takes toward the temple, and where distant pillars sit, and back-solve the current fork without needing the guide's clue at all. Building on demand means that information doesn't exist yet to be read.
- **The invariant**: at the moment any fork is being decided, no geometry beyond that fork's own two branches exists. Verified numerically — at fork N, exactly N sections exist, for all N in 1..6.
- **What changed**: `buildJourney()`'s single `for (k = 1..N_FORKS)` loop was split into `buildFork(k)` (pillars + both branches + curtain, planted at the current cursor) and `extendPastFork(k)` (the trunk beyond it, or the final approach, then `buildFork(k+1)`). The loop's locals `cursor`/`phase` became module state `journeyCursor`/`journeyPhase`, since the loop is now spread across choices rather than running in one pass. `buildJourney()` now lays only the intro trunk + fork 1; `choose()` calls `extendPastFork(forkIndex)` on a correct pick, before it reads `sec.trunkAfter`/`sec.approach` (which is what fills them in). A wrong pick builds nothing.
- **Why building at choice-time is safe** (rather than partway through the walk, as first sketched): the new geometry lands well beyond the current fork's curtain, and that curtain hasn't begun dissolving yet — `updateCurtains()` only trips `opening` once the walker is within `CURTAIN_OPEN_LEAD` (1.6) of it, and the curtain sits `CURTAIN_DIST` (~1.84) past the fork, so at choice-time the walker is still ~0.24 units short of the trigger. It's hidden from the moment it exists, with none of the mid-walk state machine deferring would need. Confirmed by eye in player view: the fog curtain fully masks where the path stops.
- **Ordering is byte-identical** for a full correct run: the sequence of `scatterAlong` calls is still intro → f1-left → f1-right → trunk1 → f2-left → f2-right → trunk2 → …, so the stone-variant round-robin and curtain/pillar array order are unchanged. Only forks never reached go unbuilt.
- **Files**: [src/main.js](prototype-threejs/src/main.js) — journey section header rewritten to document the invariant; `templeHeading()`, `buildFork()`, `extendPastFork()`, rewritten `buildJourney()`; `journeyCursor`/`journeyPhase` module state; `choose()` calls `extendPastFork()`; stale "whole route built up front" comments at the top of the file corrected.

### WebGL context creation failure on some browsers/GPUs
- **Status**: ✓ Mitigated (root cause is environmental, not fixable in this code)
- **What**: The game got stuck on the loading spinner forever in the user's own browser (Firefox on Windows), with console errors `WebGL creation failed: * tryANGLE (FEATURE_FAILURE_EGL_NO_CONFIG) * Exhausted GL driver options. (FEATURE_FAILURE_WEBGL_EXHAUSTED_DRIVERS)`. This is Firefox's ANGLE layer trying every backend it knows for that GPU and failing to get a context at all — a driver/GPU/browser-combination problem, not something wrong in the game's code. It didn't reproduce in the dev preview browser (different GPU/driver stack).
- **What changed**: `new THREE.WebGLRenderer(...)` was a single call with `{ antialias: true, powerPreference: 'high-performance' }` — the `high-performance` hint forces the discrete GPU on hybrid-graphics laptops, which is often exactly the GPU a blocklisted driver combination fails on. Renderer creation now retries with progressively safer options (drop `powerPreference`, then drop `antialias`, then accept `failIfMajorPerformanceCaveat: false` as a last resort) before giving up. If every attempt still fails, the loading spinner is replaced with an actual on-screen message (enable hardware acceleration / update GPU drivers / try Chrome or Edge) instead of hanging silently forever — that part is guaranteed to help regardless of whether the retries themselves fix any particular machine.
- **Files**: [src/main.js](prototype-threejs/src/main.js) — `createRenderer()` helper wrapping the `WebGLRenderer` construction in a `try/catch` retry loop, right after the `renderer / scene` section header.
- **Caveat**: this cannot be verified from here — the dev preview's GPU/driver stack doesn't reproduce the failure, so there's no way to confirm the retries actually help on the affected machine, only that they don't break the working case (confirmed: preview still loads and reaches fork 1 normally). If it still fails after this, the next step is the browser's own hardware-acceleration/GPU settings, not more code changes.

### Stage 2 — the Lava Cavern (design agreed 2026-09-08, performance spike built 2026-09-09)

- **Status**: The **performance spike is built and playable** at `?cavern=1`. #### Design decisions (Luke, 2026-09-07/08, answering a numbered question list)

1. **Same scale as Sky Path.** Islands, bridges and pacing all stay as they are; the cavern is big enough to hold "a diameter of more than 12 islands."
2. **Spoke angles are not 360/n.** Luke revised his own first statement here: two teams sit at **90° apart, not 180°** — "that would mean the teams can't see each other." Three at 120°, four at 90°. Spokes should match the number of teams actually playing.
3. **Same fork mechanic for now**: two branches, wrong pick breaks the bridge and drops you, same as Sky Path. New lava-themed island art is coming — mark the cavern's own instances as "lava islands" to keep them distinguishable.
4. **No guide in stage 2.** The guide becomes an ordinary player. Instead of one relayed team choice, **each player answers their own question independently**, and the questions differ per player (or at least arrive in a different order). Questions still float above the bridges as they do now, just with more text than a single word — Luke: "It's really not a big change visually. Don't even worry about that for now."
5. **Every player has their own position.** This is the load-bearing consequence of (4) and the reason the actor model moves onto the critical path — see below.
6. **Build it separately from Sky Path for now**: "Make it a separate thing for now and we'll stitch them together once they're ready." A combined "full mode" spanning both stages comes later.
7. **The doors-fade is the whole transition** between stages. Nothing else to author.
8. **Fog**: Luke's read is that the fog curtains no longer hide anything meaningful, since the words don't appear until the player reaches the next island and the two branches look identical — they're a holdover from when one branch was visibly missing. **This is still unconfirmed and was left open** when the conversation moved on; worth resolving before relying on it either way, because the "build one fork at a time" anti-cheat property is real and separate from the fog.

#### Seeing other teams — the reality check, and the chosen approach

Luke asked for options before any coding, worried this was the expensive part. The conclusion was that **it is cheaper than it looks, but the cost has moved somewhere unexpected**:

- **All three options need identical networking.** Whether a team appears as a walking avatar, an in-world beacon, or a bar on the side of the screen, the data sent is the same. Rendering is a separate, swappable decision made later — so this choice does not lock in cost.
- **Movement is not free-form**, so there is no need to stream positions at high frequency. A player holds a button and walks a known route at a known speed; position is essentially one number.
- **Luke's own simplification made it cheaper still**: players don't need to be seen continuously. They're visible standing **on islands**; when they leave you see them walk for a second, then they vanish until the next island. That turns position sync from a continuous stream with dead-reckoning into a handful of **discrete events** per player per gap ("arrived at island N", "left toward the left branch"). Applies to Sky Path too, not just the cavern.
  - A useful hybrid if smoothness is wanted at distance: keep *avatars* discrete, but let a distant team's *marker* interpolate smoothly between islands — a marker moving along a known route at a known speed is nearly free.
- **Three options, in rising cost**: (1) a side-of-screen progress list; (2) **in-world markers** — name tag and beacon at the team's true position on their real spoke, reusing the existing screen-space name tags; (3) full avatars walking their spokes.
- **Chosen: option 2**, with option 3 as a later upgrade. Rationale: at this scale another team is 150–200 units away and a character card is ~1.25 units wide — a handful of pixels through haze. The full-avatar version *only reads if you also add a marker*, so most of the expensive option's value comes from its cheap part. Luke agreed, and asked about lower-detail assets for distant teams (see below).
- **Lower-detail distant assets: yes, and there's precedent in this codebase.** The temple is already a flat billboard because it's distant. The real budget on a mid-range phone is **overdraw, not polygons** (see the fog curtain's own notes), and a distant spoke covers very few pixels. The thing to watch is *draw calls* — solved the way the fog puffs and stones already solve it, with `InstancedMesh` for distant islands and a simple strip instead of individual plank meshes.

#### The actor model — now built, in the cavern (2026-09-09)

**Built and running** in [lavaCavern.js](app/src/cavern/lavaCavern.js), deliberately *not* in `skyPath.js`. The reasoning, with the numbers that decided it: Sky Path's player state is 14 module-scope variables (`walker`, `facing`, `leg`, `forkIndex`, `walkPhase`, `holdingForward`, plus the `falling`/`rescue`/`abduction`/`templeEntry` singletons) totalling **~530 reference sites** across 2,200 lines. That is the wrong place to *discover* the right shape, because every mistake risks a working game. The cavern module is new, small, and depended on by nothing — so the shape was worked out there, to be adopted by Sky Path once proven. This is the job `crowdHarness.js` was written to inform, done somewhere it can be seen running.

- **Nothing about a walker is module-scope any more.** Each actor owns its position, facing, waypoint queue, progress and phase. **The local player is simply `actors[0]`** and has no special state — only a different source of input (the held button, versus a timer for the bots). That property is what makes this portable back into Sky Path.
- **Luke's island-only visibility rule is implemented** and is the thing that makes remote players cheap: an actor is drawn while standing on an island, plus a 1-second tail after departing (`DEPART_VISIBLE_SECONDS`), then hidden until it arrives at the next island. The local player is exempt.
- **Beacons** hold a constant *apparent* size (scaled by distance to camera) rather than a constant world size — at 200 units a fixed-size marker is as invisible as the card it advertises. One colour per spoke, so which team a distant beacon belongs to reads at a glance.
- **The other players are locally-simulated bots**, not networked. They stand on an island for a random dwell, then cross. This exists to judge how the *rendering and visibility* read, which was the open question; the relay that eventually drives them only has to set the same fields the bots set.
- **Measured: actors are effectively free.** 16 actors cost **+9 draw calls** over an empty cavern; **32 actors (4 spokes × 8 players) measured 196 draw calls / 1023k triangles / ~100fps — no measurable change at all**, because the visibility rule hides most of them at any instant. **The cost is the world geometry, not the people in it**, which retires the main worry about option 3 (full avatars) as well.

Luke, after watching bots pop in and out: "given how little is actually visible of the other players even when they are at maximum visibility, would it create problems if we were to remove that mechanism for other island spokes... and have the players from other teams visible at all times?" Assessed first (no real cost concern — `stepActors()` already updates every actor's position every frame regardless of visibility, so this was always just a `.visible` flag away), then built:

- **The island-only/departure-tail rule now applies only to the local player's own spoke.** Any actor on a *foreign* spoke is drawn continuously through its entire crossing, not just the first `DEPART_VISIBLE_SECONDS`. Teammates on your own spoke keep the original rule — verified directly: a teammate mid-crossing past its 1-second tail measured `visible: false`, while every foreign-spoke actor mid-crossing at the same moment measured `visible: true`, matching the scoping exactly.
- **Cost, measured at the worst case** (rim, 4 spokes × 8 players, i.e. double the roster of the earlier "actors are free" measurement): **239 draw calls / 1035k triangles**, up from 194/1031k under the old rule with half the roster. Triangle count barely moved (draw calls are the real cost of more simultaneously-visible cards+beacons); still well short of anything alarming, but no longer literally free the way the hidden-by-default measurement was. If this becomes a problem on a real phone, the fallback already identified is instancing the foreign-team markers into one `InstancedMesh` per team (position/tint per instance) — the same trick already used for the fog puffs and stones.
- **A fall marker.** Bots now have a placeholder 25% chance (`FALL_CHANCE`) of failing a crossing — stopping at the bridge's midpoint (echoing Sky Path's own `BRIDGE_WRONG_GAP_T` treatment) rather than reaching the far island — showing a small red "!" icon above the beacon, then recovering onto the island they departed from after `FALL_RECOVER_SECONDS`. The icon is a separate mesh from the beacon (canvas-drawn, not an art asset) so team colour and fall state read independently — you can tell *who* fell without losing *which team* they're on.

Confirmed why: Sky Path's own atmospheric fog uses a light sky-blue that contrasts against its darker foreground; the cavern's fog colour was close to the scene's own ambient dark-orange/brown palette, so at any near/far setting it blended in rather than reading as depth. `scene.fog` and both sliders are gone. If atmospheric fog is wanted again, it needs a genuinely contrasting colour, not just a re-tuned range.
- **"s / island" investigated — not broken, just nearly invisible under the old rule.** Confirmed via the debug hook that the slider correctly writes `TUNE.secondsPerIsland` and `walkSpeed()` reads it live. The reason it looked like nothing was happening: under the *old* visibility rule, a walking bot was only ever drawn for the fixed first second of a crossing regardless of the crossing's total length — so changing the pacing mostly changed an interval nobody could see. Local-player speed is also only demonstrable while actively holding ▲. Now that foreign spokes are always visible for their whole crossing, a bot stays on screen long enough for a pacing change to be obvious without touching anything else.
- **A found-and-fixed bug, worth recording**: forcing a bot into the fallen state directly (for testing) without going through `nextLeg()`'s normal `gapIndex` increment let the recovery step decrement `gapIndex` below zero, crashing the next `nextLeg()` call on an out-of-range array access. #### Defaults locked, camera-spin bug fixed, look-around added (2026-09-10)

Luke judged the spike on his own phone and gave final numbers: `ringHeightFrac` 0.5, `spacing` 40, `islandsPerSpoke` 6, `playersPerSpoke` 4, `secondsPerIsland` 5.2, `camBack` 9.5, `camHeight` 3.8. All baked in as `TUNE`'s own defaults (sliders kept live for the next art pass). Tuner now starts collapsed. One side effect worth knowing: raising the ring height to 50% shrinks the dome's own wall radius at that height, so the "wall gap" (the empty lava moat past the rim island) dropped from 164 units to **20** — still present, far less generous than it was.

- **Camera-spin bug, found and fixed.** Luke: "when the player moves from the first island to the second, just as they reach the bridge, the camera quite rapidly spins 360 degrees around the player. It only happens at this point." Root cause: the heading-easing code used the textbook "wrap to ±180°" one-liner, `((delta + π) % 2π) - π` — but that assumes FLOORED modulo (Python's `%`); JavaScript's `%` is a truncating remainder that keeps the sign of its left operand, so for a delta landing in `(-2π, -π)` the "wrap" silently does nothing, leaving the correction nearly a full turn instead of a few degrees. Only visible on the very first crossing because that's the one moment `facing` starts completely at rest with zero prior easing — every later crossing is already tracking closely, so its correction is small and never lands in the broken range. Fixed with a plain conditional (`wrapAngle()`) that doesn't rely on modulo semantics. **Sky Path's own `tick()` has the identical formula** — not touched, since it apparently hasn't been observed to trigger there, but it's the same latent bug.
- **Look-around added, deliberately NOT Sky Path's technique.** Luke: "bring in the ability for the player to look around a bit, like they can in Sky Path... I want the player to be able to look up towards the top of the cavern a bit." Sky Path's drag-to-look is a positional SLIDE (camera shifts sideways, gaze target fixed) built specifically to sell parallax between its flat 2D backdrop layers — it can't plausibly swing far enough to look up at a real dome overhead. So this is a genuine aim ROTATION instead: same interaction shape (captured pointer, eased target, clamped range), applied to where the camera looks rather than where it sits. Yaw ±50°, pitch 20° down to **65° up**. `restDy` bakes in Sky Path's own `CAM_LOOK_Y` convention so pitch=0 reproduces the exact pre-existing resting gaze — drag only adds swing on top of it. Verified by screenshot: dragging up shows the dome's vent hole and rock ceiling; dragging sideways shows the wall off to the side.

#### Lava shader (2026-09-10)

Luke supplied two source photos (Desktop: Lava1.jpg, LavaDark.jpg — not committed, only the processed textures are) and asked for an assessment before building. **Neither tiles seamlessly** — confirmed by rolling each by half its size (a standard seam-check) and finding a visible grid line at the join, worse on LavaDark. A "force it seamless" mirror-tile attempt was tried and rejected: technically seamless, but obviously kaleidoscopic (a mandala, not lava).

- **What actually works, confirmed by testing a static approximation before writing the real shader**: two layers at DIFFERENT tile frequencies (not just different offsets — same-frequency offset copies keep the same grid, just translated) plus a fixed rotation between them. Matching-frequency and offset-only tests still showed the grid; genuinely different frequencies visibly disguised it. This is the same technique the fog curtain's own shader already uses (three samples of one noise texture at different scales/drift directions) — reused here across two distinct source images rather than reinvented.
- **Built**: [lavaCavern.js](app/src/cavern/lavaCavern.js)'s lava section — a `ShaderMaterial` on the lava disc sampling Lava1 (base) and LavaDark (overlay, reduced alpha — Luke's own "at least one with reduced alpha" idea) at scales `1/50` and `1/33` world units (a non-harmonic ratio, so their periods never coincide), independent drift directions, a fixed ~24° rotation on the second layer, and a cheap analytic sine-based "domain warp" (no extra texture fetch) bending both away from straight lines. Stress-tested at 2.8× the shipped tile frequency and the grid still didn't read as one — the shipped default should be comfortably clean.
- **Assets reprocessed, not shipped raw**: sources were 3.1MB/7776² and 2.3MB/8000² — vastly more than a shader sampling a distant, constantly-scrolling surface can ever show. Cropped to a smaller non-repeating region, downscaled to 1024², re-encoded as WebP (matching the project's existing convention for large photographic textures, e.g. `cloud-dense.webp`): **170KB + 60KB**, down from 5.4MB combined. [lava-1.webp](app/public/textures/lava-1.webp) / [lava-dark.webp](app/public/textures/lava-dark.webp).
- **Cost**: one draw call, same as the flat-colour placeholder it replaced — confirmed via `renderer.info.render.calls` before/after (215 either way). Three new tuner sliders: `lava dark %`, `lava speed`, `lava scale` (the last multiplies both layers' frequency together, preserving their ratio).

#### Lava: fake relief, softer dark layer, slower base (2026-09-11)

Luke asked whether real 3D geometry (a contoured mesh, textured and animated) could make the lava read as less flat, before any other changes. Checked one concrete fact first: `THREE.CircleGeometry` — what the lava disc actually uses — is a single fan of triangles from one centre point straight to the outer ring, with **no vertices anywhere in between** (confirmed by reading its source). So today's disc physically cannot show a bump; any geometry approach needs a different mesh first (a subdivided grid, circular-clipped in the shader). That's real work, and it needs actual shading to sell the bumps once they exist, since this project's whole style is unlit ("shading painted into the art").

Given that, recommended trying the cheapest version first — colour-only fake relief, no geometry, no lighting — and revisiting real displacement only if it still reads flat. Luke agreed. Built, along with the two fixes he'd flagged:

- **Fake relief via colour** (`heightField()` in the shader): an independent sine field (deliberately not the same field driving the texture warp, so the "bumps" don't look mechanically locked to the distortion) brightens peaks and darkens troughs, with a slight warm push at the highest points (hot lava reads brighter *and* more yellow, not just brighter). New `lavaRelief` slider/TUNE value (default 0.35, 0 = flat as before) — confirmed visibly doing something by comparing screenshots at 0 vs default.
- **LavaDark no longer straight colour-mixed.** Luke: "the sheet under it is a bit too visibly exactly what it is: another image moving in a different direction." Diagnosis: a straight `mix()` shows two distinct crack networks in two distinct colours at the same time, which is exactly what gives away "two photos." Fixed two ways together: (1) LavaDark's own texture asset was re-processed with a gaussian blur (`-blur 0x6`) so its linework softens into blobby mottling instead of competing with the base layer's own cracks; (2) the shader now uses LavaDark's *luminance* to multiply the base colour's brightness rather than blending its colour in — it can only darken, never introduce a second hue/line network, so it reads as shadow on the lava rather than a second lava.
- **Base layer (Lava1) slowed to 30%** of its previous drift speed — Luke: "moving a bit too fast." LavaDark's own speed is untouched; only `LAVA_SPEED_1` was scaled, not the shared `lavaSpeed` multiplier (which would have slowed both layers together).
- **Still open**: real vertex displacement (the actual 3D-mesh idea) hasn't been ruled out, just deferred behind trying the cheap version first. If the colour-only relief still isn't enough once Luke sees it live, the next step discussed was a fake normal-map (derive one from the lava texture's own brightness, light the flat disc against a fake lava-only light direction — no geometry, no CPU cost, likely the best payoff per unit of effort for a surface that's mostly seen from a distant/grazing angle) before reaching for real geometry.

#### Fake normal-map lighting, and two sandbox gotchas worth remembering (2026-09-11)

Luke asked for the fake normal-map (previous entry's "still open" item) after hearing the explanation. Built as `estimateNormal()` in the shader: three samples of the Lava1 texture already loaded (centre, +x, +y) stand in for a height map — no second asset, no geometry. New `lavaBump` slider/TUNE value (default 6) controls how strongly a brightness difference between neighbouring texels is read as a tilt; a fixed made-up light direction (lava self-illuminates, doesn't need to match the scene) lights it, centred on the flat-surface response so an untilted patch is untouched.

- **A real bug, found via the Vite error overlay**: the shader's own header comment used backtick-quoted \`flatN\` for emphasis — inside a JS template literal (the whole shader is a backtick-delimited string), a literal backtick inside a `//` comment still closes the *outer* JS string, corrupting everything after it. Fixed by dropping the backticks from the comment. Worth remembering for any future GLSL-in-template-literal comment in this file.
- **A sandbox dead end, worth recording so it isn't re-walked**: `canvas.toDataURL()` on a `THREE.WebGLRenderer`'s canvas reads back solid black in this environment — a known gotcha (the drawing buffer isn't preserved by default, so a readback after the fact gets a cleared buffer even though the actual on-screen frame, captured via a real screenshot, is correct). Don't use `toDataURL`/`readPixels` to sanity-check a Three.js canvas here; trust the screenshot tool instead.
- **A wrong turn, corrected**: mid-investigation this file speculated that the look-around's 20° down-pitch limit was too shallow to ever see the lava floor at all, and that testing had actually been looking at the dome wall's own baked-in lava-vein texture rather than the disc. **Luke corrected this directly**: "the down-look limit is fine: I can easily see the lava floor. In fact it can be easily seen even without 'looking down', in the default 'forward' view." So that theory was wrong — worth noting only so it isn't treated as settled fact later.
- **Reverted.** Luke, after checking the built version: "something you did has removed the lava; it now looks completely black. I suggest you undo the normal map." Root cause, now understood precisely rather than guessed at: the fixed light direction (`vec3(0.35, 0.9, 0.3)`) was chosen assuming z (pointing straight out of the flat surface) would dominate the response, keeping most points close to the flatN baseline — but 0.9 on the *y* component (a texture-tangent direction in `estimateNormal`'s basis, not world "up") actually dominated instead. At the bump strength needed to see anything, most points end up with their fake normal tilted mostly in that tangent plane, whose direction relative to the light is effectively arbitrary — so `max(dot(normal, light), 0.0)` clips to zero at a large fraction of points, and each clipped point darkens by a fixed fraction. Compounding multiplicatively with the existing dark-layer and relief terms, this crushed the whole surface toward black rather than embossing it. **Fully reverted** — `estimateNormal()`, the `uBump` uniform, `TUNE.lavaBump`, and its slider are all removed; the shader is back to exactly the fake-relief-plus-dark-layer-plus-slower-base state from the previous entry, **but that alone did not bring the lava back** — see the next entry. A real normal-map attempt, if revisited, needs a light direction and a normal-construction basis that are actually consistent with each other — worth designing on paper before writing the shader next time, not tuning by eye after the fact.
- **The lava was never rendering at all — the shader failed to compile (fixed 2026-09-11).** Luke, after the revert: "the lava is still invisible... I always do a hard refresh after any change; it's never a caching issue. I even opened it in a completely different browser." He was right and the caching theory was wrong. Decisive test: swapping `lavaMat` for a flat magenta `MeshBasicMaterial` drew an unmistakable disc in the default forward view, so mesh/position/scale/orientation were fine and the fault was inside the shader. Console then showed `THREE.WebGLProgram: Shader Error ... 'luminance' : function already has a body` and `useProgram: program not valid` every frame: three.js's own shader prelude now declares `float luminance(const in vec3)`, and the fragment shader's local `luminance()` helper (dead code — the dot product was already inlined) collided with it, so the program never linked and the disc was skipped entirely. **Every "warm orange visible in screenshots" verification in the preceding entries was actually the dome wall's own baked lava-crust texture, not the disc** — this is exactly the wall-vs-floor ambiguity that was raised earlier and then dropped. Fix: delete the helper. Lessons: (1) a ShaderMaterial that won't compile is rendered as *nothing*, so "the lava looks black/missing" is compile-error-shaped, not tuning-shaped — check the console for `WebGLProgram` before touching a uniform; (2) don't verify a floor is rendering by looking for its colour when the walls are the same colour — use an unmistakable stand-in material; (3) `window.__cavernLava()` now exposes the material so its uniforms and texture arrival can be read from the console; (4) the preview browser buffers console output per tab across reloads and throttles rAF in background tabs (uTime stayed at 0, fps 0) — open a fresh tab and front it before trusting either.


#### The world's cost, and what remains for Sky Path

#### The spike, as built ([app/src/cavern/lavaCavern.js](app/src/cavern/lavaCavern.js), `?cavern=1`)

Built to answer one question that reasoning could not: Sky Path's fog curtains mean only ~1–2 islands and ~2 bridges are ever on screen, but a four-spoke cavern puts **25 islands and 48 bridges** in view at once. That is 10–20× the visible content.

Before the dome grew (V3, spacing 15, camera at Sky Path's own 7.3) it was 187 / 571k — draw calls barely moved, but longer bridges nearly doubled the triangles, because plank count scales with span.

#### Gotchas found while building it

- **The island `.glb` must be rescaled and its deck textured.** The model's own scale depends on where a tuning slider sat at export time, so the deck's real radius has to be measured **off its vertices** (a `Box3` around a flat disc is a square, and its bounding sphere overstates radius `r` as `r√2`) and the whole model scaled to `ISLAND_RADIUS`. Skipping this filled the screen with one enormous island. `lavaCavern.js` now mirrors `skyPath.js`'s handling.
- **The dome is converted to unlit `MeshBasicMaterial`**, per CLAUDE.md's rule and because a sphere lit from the inside is exactly where normals fight you.
- **Dome dimensions are measured from the loaded model, not hardcoded** — V3 was 200 across, V4 is 600 — so the next dome needs no code change at all.
- **Testing on a phone**: the dev server is already LAN-exposed (`server: { host: true }` in `vite.config.js`). When Luke's phone couldn't reach it, the likely causes in order were Windows Firewall blocking node on private networks, the phone not actually being on the same Wi-Fi, router AP/client isolation, or a changed DHCP address.

### Cardboard lettering: name tags and signage (in progress, started 2026-08-29)

- **Goal**: cardboard-cutout-style text — first use is floating name tags above player avatars, likely reused for title screens/signage later. Letters are photographed cutouts (corrugated flute pattern visible through the cut), composited onto a stretchable cardboard-background texture.
- **Status**: **live in the actual game as of 2026-08-30**, not just previews. The full 52-letter alphabet (upper + lower) is extracted, cleaned, and verified — [app/public/textures/letters/upper-v2/](app/public/textures/letters/upper-v2/) and [app/public/textures/letters/lower/](app/public/textures/letters/lower/), `A.png`–`Z.png` / `a.png`–`z.png`. The character-select screen has a "Name your character" field (max 10 letters, non-letters stripped, first-capital-rest-lowercase), and hitting Start builds a real name-tag texture and hangs it above the local player's own card — see [app/src/skypath/nameTag.js](app/src/skypath/nameTag.js) (the runtime renderer) and its wiring in `skyPath.js` (`attachNameTag`, called from the `charStart` click handler). Verified by pulling the actual `CanvasTexture`'s canvas out of the live running scene (`window.__rig`/scene-traverse trick) and inspecting it directly, not just screenshotting — catches anything a screenshot's scaling would hide.
- **First attempt failed and was abandoned — worth knowing why, so it isn't retried.** The original source was two sprite-sheet photos (one grid image per case, `Assets/Alpha Upper Case.png` / `Alpha Lower Case.png`), extracted by automated segmentation (grid math + darkness threshold + connected-components cleanup). This broke badly: roughly half the uppercase letters came out with debris fused in, split counters, or bled into neighboring letters, even after several rounds of fixing (documented, then superseded — the working files from this attempt were deleted 2026-08-29). Separately, the lowercase sheet was mostly *wrong content*: only 8 of 26 glyphs (`a b c d e f g i`) were genuinely lowercase forms; the rest were duplicate uppercase letterforms. **The root cause of the segmentation failures wasn't fixable with more tuning**: one global setting can't serve 26 different letters sharing one photo, each with different stroke widths, counter sizes, and proximity to the photo's own artifacts (a physical fold crease, corner vignetting, torn edges) that read as "letter-dark" exactly like real strokes do.
- **The fix: one photo per letter**, supplied as `Assets/Upper Alphabet/{A-Z}.png` (circular crops) and `Assets/Lower Alphabet/{a-z}.jpg` (rectangular). This removes neighbor-bleed entirely and makes per-photo tuning tractable, since each photo only has to satisfy one letter's shape. Confirmed working via full re-extraction of both alphabets with a real zoomed QA pass on every batch (not just a shrunk contact sheet — that's what let the sprite-sheet failures slip through originally).
- **Circle vs. square crop**: doesn't affect extraction difficulty at all (confirmed to Luke 2026-08-29) — only affects safety margin, since a circle throws away corner area a wide/flourished letter might need. Checked M and W (the widest uppercase letters) specifically against the circular crops actually supplied: both had comfortable clearance, so square wasn't actually necessary for this alphabet, but would be the safer default for anything with wider serifs.
- **Recurring technical gotchas, worth knowing before touching this again**:
  - **Never flatten the source's transparency onto a synthetic color before the final composite.** Doing so bakes that flat color into every letter's soft edge pixels — invisible against a backdrop that happens to match, but shows as a visible halo against anything else (found comparing letter G against a mismatched gray, 2026-08-29). Flatten-to-a-fixed-gray is fine for the grayscale/threshold *analysis* step (it avoids a separate bug where fully-transparent corner pixels read as black and get misread as letter-dark) — just don't use that flattened version for the RGB that actually gets shown; composite against the source's raw pixels instead.
  - **The corrugation pattern inside each letter alternates between very dark and medium-bright bands** — medium-bright bands can be as light as the surrounding cardboard, so a plain darkness threshold alone leaves letters looking like venetian blinds. Fixed with a morphological *closing* step (`-morphology Close Disk:7` in ImageMagick) to bridge the gaps into one solid shape. Too small a radius leaves stripe-gaps or splits ring letters (O) into disconnected arcs; too large distorts tight features like B/D's counters. Disk radius 6–7 is the calibrated sweet spot for this art style — re-check if the physical stencil/corrugation changes.
  - **Debris cleanup must filter by an absolute area cutoff, not "keep only the largest blob."** `-connected-components ... keep-top=N` ranks background alongside the letter, and background is usually the single biggest region by area — so `keep-top=1` reliably keeps *background* and silently deletes the letter (found on Q and Z in the sprite-sheet attempt, and independently on the standalone `g` photo which had a real crease/fiber patch). The working approach is `-define connected-components:area-threshold=N` (drops anything smaller than N, keeps everything else's real value) — calibrate N per source batch: real small features that must survive (i/j's dot, ~1250–1300px²) have to stay above the cutoff, while noise (a few hundred px² or less) has to stay below it.
  - **Expect per-photo threshold tuning, not one global setting.** Lighting/grain isn't perfectly consistent shot-to-shot — several letters across both alphabets (uppercase C; lowercase k, s, w, x, y, z) needed a stricter darkness cutoff than the default to exclude fiber-texture noise the default threshold let through. `g`'s lowercase photo additionally needed a small crop to exclude a rough patch in one corner.
  - **Check file hashes on a fresh batch before extracting.** The original `p.jpg`, `q.jpg`, `r.jpg` in `Assets/Lower Alphabet` were byte-identical to `o.jpg` (confirmed via `md5sum` — all four the same "O" photo, cause unknown, Luke didn't know how it happened either). Caught before wasting an extraction pass on wrong content; re-supplied and re-extracted correctly. Worth an `md5sum` sanity pass on any new letter batch.
- **Four layout constants, tuned live via a slider prototype and now FINAL** — don't re-derive without cause; if the source art changes, re-open the prototype rather than guessing new numbers:
  1. **Lowercase renders at 70% of uppercase height** (agreed 2026-08-29) — a deliberate typographic choice, not derived from the photos (the raw extracted photos have no consistent relative scale between letters at all, since each was shot independently).
  2. **Descender letters (g, j, p, q, y) shift down 6px** from a naive bottom-aligned-bounding-box position (agreed 2026-08-30). Necessary because there's no real font-baseline metadata — only each glyph's tight trimmed bounding box — so bottom-aligning that box makes a descender's *body* sit visibly higher than non-descender letters (its box is taller to make room for the tail). This surfaced clearly when actually rendering words ("Sparrow"), not from looking at letters in isolation.
  3. **Lowercase `j` renders at 115% size** (agreed 2026-08-30) — Luke's call that it looked "too small/thin" next to the other lowercase letters at its natural extracted size.
  4. **`j`'s side gaps grow proportionally with its size** (also 115%) — so the enlarged glyph doesn't crowd its neighbors; confirmed by measuring actual rendered pixel positions (o/j/e gaps), not just eyeballing it.
  - Tuned via [app/descender-tuner.html](app/descender-tuner.html) — a standalone page (same pattern as `island-proto.html`/`bgTuner.js`) with live sliders driving the actual extracted letter images, showing "pygmy" and "quojen" (chosen to exercise all five descenders plus non-descenders for contrast) and reproducing the exact problem before the fix. Reusable if either constant needs revisiting.

- **Glow/outline, added 2026-08-30**: the letters read poorly at actual small on-screen name-tag size, so `nameTag.js` now draws a colored glow behind each letter before the crisp letter itself. Built from the glyph's **alpha channel only**, via the canvas `shadowColor`/`shadowBlur` trick on `drawImage` — canvas shadow is computed from whatever's drawn's alpha, never its RGB, so this cannot trace the internal corrugation stripe detail (which lives entirely in RGB) even in principle, only the true letter silhouette. Color options were tested side by side at both full resolution and a simulated small size (white, gold, cyan, near-black): white and near-black essentially disappeared once shrunk, cyan was the most legible but reads as neon rather than a cardboard sign, gold (`#ffd54f`) was the best balance and is the default.
  - **First pass (2 passes, blur 7) was confirmed too subtle** ("still not very visible," Luke, 2026-08-30). Thickness (`shadowBlur`) and brightness (repeated shadow passes — the shadow color is already fully opaque, so "brighter" means re-saturating the blurred edge by drawing it again, not raising an alpha that's already maxed) became live sliders, bottom-right behind `?tune=1`. Defaults bumped to blur 12 / 4 passes as a starting improvement.
  - **Then it appeared to do nothing at all** ("no effect I can see," Luke) — two compounding bugs, both fixed 2026-08-30:
    1. The tuning object's keys (`blur`, `passes`) never matched what `buildNameTagCanvas` actually reads (`glowBlur`, `glowPasses`); the spread into its options silently produced keys it didn't recognise, so every rebuild quietly used the hardcoded defaults regardless of slider position. Fixed by renaming the tuning object's keys to match exactly (`glowBlur`, `glowPasses`, and now `gamma`/`contrast`/`saturation` too).
    2. Separately, the tag is small on screen for nearly all of normal play, so the GPU constantly minifies this texture — THREE's default mipmapping *averages* neighbouring pixels per mip level, which was diluting a thin glow outline to barely-there before it ever reached the screen. Confirmed by scaling the mesh up 5x in place to inspect it un-minified — the texture itself was correct, only the minified render was washed out.
  - **The mipmap fix then caused a new bug**: disabling mipmaps (`LinearFilter`, no mips) stopped the dilution but reintroduced texture aliasing against the moving camera — Luke saw this as "a moving, strobing glow." Reverted to THREE's normal mipmapped filtering (stable, matches every other texture in the game) 2026-08-30; the glow is subtle again as a result, an accepted trade since the glow approach was put on hold in favour of gamma/contrast (below). See `makeNameTagTexture`'s comment in `skyPath.js` for the full history if this gets revisited — the real fix is likely a thicker source-canvas outline so more of it survives mip-averaging, not fighting the mipmap system.
- **Gamma/contrast/saturation, added 2026-08-30 — the alternative Luke reached for** after a still-image photo-viewer test on the raw cardboard found gamma made the biggest readability difference, more than the glow. Applied once to the whole composited canvas (background + letters + glow together, via `applyPostFX` in `nameTag.js`) — contrast/saturation are native canvas filter primitives, gamma needed a manual per-pixel remap (`getImageData`/`putImageData` through a 256-entry lookup table) since canvas has no gamma filter primitive; both are one-time costs per name, not per-frame.

Kept in sync in `render-cardboard-text.sh` too (`GAMMA`/`CONTRAST_PCT`/`SATURATION_PCT`), though that script's contrast/saturation are only an *approximation* of the canvas version — ImageMagick's `-brightness-contrast`/`-modulate` use different curves than CSS `contrast()`/`saturate()`, while `-gamma` maps exactly onto the canvas math (same `input^(1/gamma)` formula) — so treat that script's color output as "close enough for a fast preview," not pixel-identical to what ships in-game.

### Path shape iteration is broken as a process — build a live tuning prototype (agreed 2026-08-28)

- **Status**: Agreed as the next step, but explicitly **not immediate** — Luke wants to do the cardboard name-tag work first (see its own entry). Written up in full now because context will not survive compaction, and this needs to be actionable from cold.
- **The symptom**: after several rounds of adjusting the fork-branch path shape (see "Fork branches: both routes lead to the same island" in Completed for the blow-by-blow — a crossing bug, a lens-vs-hourglass direction error, an angle/pinch budget that went negative when islands shrank), Luke's assessment on 2026-08-28 was "the path still isn't great: not quite the shape I want." Every round of feedback so far has gone: Luke describes or sketches a shape → Claude turns it into trigonometry → Claude verifies the numbers standalone (Node scripts, signed offsets, etc., since **this environment's browser preview cannot reliably composite frames or run real time** — see the falling-mechanic entry's Testing note) → Luke actually runs the game and reports whether it looks right. That loop is expensive per round and lossy in both directions: prose/sketches under-specify a curve, and numeric self-consistency checks (which is all Claude can do without eyes on the render) cannot catch "not quite the shape I want" — only outright errors like crossing branches.
- **The diagnosis**: the bottleneck is not the geometry, which is fully under programmatic control already (a handful of formulas — `genForkCurve`, `genBowPoints` — in `app/src/skypath/skyPath.js`) — it is the *feedback loop*. Neither party can iterate quickly: Luke can't adjust a curve directly, only describe the delta from what he saw; Claude can't see the delta at all, only compute what the formulas produce.
- **The proposed fix: a standalone live-tuning prototype**, the same pattern already proven twice in this project — [app/island-proto.html](app/island-proto.html)/[islandProto.js](app/src/islandProto.js) for island shape, and [bgTuner.js](app/src/skypath/bgTuner.js) for the backdrop. A page with sliders (or, better, actual draggable control points on the curve) driving the same curve-generation code live in Luke's own browser, with no round-trip through chat needed to see a change. This is a strictly more direct fix for "not quite the shape I want" than another round of described adjustments.
  - Worth building with either the current flat-billboard stones or (probably better for clarity) a plain debug ribbon/line showing the raw curve — sparse stone billboards sample the path at intervals and can visually obscure the true curve shape underneath.
  - Exposing real control points (not just the current named constants — `FORK_HALF_ANGLE`, `FORK_PINCH_WIDTH`, `ISLAND_RADIUS`, `FORK_BOW_WIDTH`/segments) would let Luke shape the curve far more directly than trigonometric parameters ever can, though even just live sliders on the existing parameters would already be a large improvement over the current loop.
- **Three goals this needs to serve, all raised by Luke and all still open**:
  1. **Better curvature** — the immediate, named complaint. The current shape (straight departure at `FORK_HALF_ANGLE`, sin-pinch toward the other branch via `genBowPoints`, mirrored straight arrival) is Claude's best reconstruction of two rounds of sketches, not something Luke has been able to shape directly. ### World scale rework: make the art the master unit (agreed 2026-08-27)

- **Status**: Steps 1–3 and Step 4 (converging branches) all done, 2026-08-27 — see Completed for "Scale rework, steps 1–3" and "Fork branches: both routes lead to the same island". 3D stones are still pending; its entry below still describes the plan accurately.
- **The problem, in one line**: path spacing and island size were two independent scale systems that were never related to each other, and they collided.
  - Path scale is derived **top-down**: `TEMPLE_DISTANCE (70) × CRUISE_FRACTION (0.75) ÷ 6 forks` → **8.75 units of forward travel per fork**.
  - Island size was chosen **bottom-up**, by eye, from what looked right on camera → **radius 6, diameter 12**.
  - 12 units of island cannot fit in 8.75 units of spacing. They interpenetrate by 3.25.
- **Symptoms this caused** (all reported by Luke, all traced to the two faults above): walking off the island's edge, across a stretch of nothing, onto a stray fragment of path, then falling; or on a correct choice, stepping from one island's edge straight onto the next with almost no gap; and later path sections sitting *inside* islands. `CURTAIN_DIST` (1.84 from the fork centre) is currently **inside** the island's own deck, which is one concrete instance of the last one.
- **The decision: the island is the base unit, and everything else derives from it.** Three reasons, all pointing the same way — the island is authored art whose proportions are a fixed creative decision, not a number to tune; stones are about to become authored art too and must relate to the island's edge and to stride; and the planned intro camera is a shot *composed around the island*, so composition wants a stable subject size. `TEMPLE_DISTANCE` stops being an input and becomes a **result** (the temple is a backdrop billboard, so its distance is free as long as it is rescaled to preserve apparent size). This is what lets `N_FORKS` vary with teacher setup without wrecking island spacing.
- **The intended relationships**:
  - `R` = island deck radius (authored; currently 6)
  - `G` = the visible path gap between two island *edges* — the one real design knob
  - `D` = fork-to-fork distance = `2R + G`
  - journey length = `N_FORKS × D`; temple distance = journey length + arrival margin
  - `ISLAND_CLEAR_R` = `R` exactly (correct only now that the measurement is right)
- **Chosen starting values**: `R = 6`, `G = 8` → `D = 20`, journey `120` (up from 52.5). At the current `WALK_SPEED 3.2` that is **~37s of walking per round**, up from ~16s. Luke accepted 37s as a starting point on the explicit understanding that **walk speed is the lever if it turns out too slow** — do not shrink the islands to fix pacing.
  - **Superseded 2026-08-28: `R` shrunk to `4`** ("make the islands about a third smaller"), giving `D = 16` and journey `96`. The advice above not to shrink islands for *pacing* still holds — this shrink was a scale/proportion decision, not a pacing one — but shrinking `R` does shrink `D` as a direct consequence of the formula above, so the walk got shorter as a side effect regardless of intent. Revisit pacing (via `WALK_SPEED`, as already agreed) if 96 reads too short, rather than re-growing the island to fix it. This shrink also tightened the fork-branch daylight budget — see "Fork branches: both routes lead to the same island" in Completed for the follow-on retune it required.
- **Sense of scale is a goal, not a side effect**: Luke wants the world to feel large. The levers agreed are **smaller characters** and **faster/further movement**, not bigger islands. `FIGURE_H` is currently `2.2 × 0.8 = 1.76`, against an island 12 across (≈6.8 character-heights). Dropping the figure to ~1.2–1.4 makes that ≈9–10 and reads much larger. Watch three things when doing it: the figure must not get too small to read in frame (`CAM_BACK 7.3` may want to come in a little, though pulling the camera *in* fights the sense of scale, so prefer a lower camera angle over a closer one); the walk bob constants (`WALK_BOB_HEIGHT` etc.) are in world units and want scaling with the figure; and `STONE_SIZE 1.0` is currently 57% of figure height but would become ~83%, so stones likely want to shrink too — though that is really a stride question, see the 3D stones entry.
- **What needs re-checking once `D` changes** (none expected to be hard, but all are in world units and none of them know about this change): `CURTAIN_DIST` (must end up *outside* the island now), fog radii `FOG_CORE_*`/`FOG_FADE_*`, `WRONG_STUB_LEN`, cloud row spacing, bird distances, and the camera's near/far planes. The far backdrop should be fine untouched — horizon at −360 and sky shell at 400 comfortably contain a 120-unit journey.

### Intro camera animation: deferred, but decided (agreed 2026-08-27)

- **Status**: **Not being built yet.** Recorded now because it constrains decisions being made today, and because one of its problems is invisible until you try it.
- **What it is**: the round opens with the camera further out from the first island, then zooms in to the current starting position.
- **Why it is written down now**: it is the main reason the **world scale rework** treats the island as the composition subject, and a strong argument for **converging branches** — because that makes island positions deterministic and known at build time, the shot can be *authored* (frame the route, show the temple, land on the start) instead of having to cope with a chain whose shape depends on choices not yet made. The rig needs an exception or a freeze for the duration of any scripted camera move. Cheap to fix once known; genuinely invisible until the shot is first tried, which is exactly why it is noted here.
- **Other things to check when it is built**: the cloud deck and land/sea deck come into view differently from further out (`CLOUD_ROW_SPACING 20`, `FLOOR_Y −40`), and the temple's apparent size changes with any camera distance change, so its scale may need re-checking against the new derived `TEMPLE_DISTANCE`.

### 3D path stones, and what the current path work does / doesn't survive into it

- **Status**: Not started. Referenced by several entries above; written up properly 2026-08-28 when Luke asked, reasonably, whether the path-shape work being done now would be thrown away once real stone meshes arrive.
- **The answer: the centreline survives, the width does not.** The path is two separate things that happen to be tuned together today:
  - **The route** — `genForkCurve()`/`genBowPoints()` and the waypoint chains they produce. `scatterAlong()` already consumes these as a pure polyline and knows nothing about what a stone *is*; `placeStone(x, z)` is the only part that touches geometry. Swapping instanced billboards for GLB meshes changes `makeStoneMesh`/`placeStone` and leaves the route untouched. **Settling the path's shape first is the right order** — it is also what the walker, the fog curtains, the fall trigger and the guide markers all read from, none of which care about stone art either.
  - **The width** — `PATH_WIDTH` (2.6), `STONE_COLS` (3), `STONE_SIZE`, `ROW_SPACING`. These are provisional by definition: real stones have their own footprint and their own sensible overlap, so all four get re-derived from the mesh. Anything tuned *against* the current paved width is therefore provisional too, which right now means `FORK_PINCH_WIDTH` and, indirectly, `FORK_HALF_ANGLE`.
- **The concrete open question this hands over** (see the converging-branches entry for the full working): a path is currently ~2.45 wide against islands 12 across — ~20% of island diameter, where Luke's illustration of the intended look implies nearer 12%. That width is what stops the two branches pinching as close as the illustration shows, and it gets *tighter* if islands shrink as planned. So the stones work should treat "how wide is a path, in island-radii" as a **design input to decide**, not an output to inherit — probably by choosing stone size from stride first, then picking `STONE_COLS` to hit a target width fraction.
- **Also relevant**: `STONE_SIZE` is deliberately `1.0 × FIGURE_SCALE` — stones are sized relative to the *character*, not the world (see the scale-rework entry; Luke corrected an earlier pass that had this backwards). Real stone meshes must keep that relationship: they are things a person steps on, and their size is a stride question first and a scenery question second.
- **One deferred behaviour needs per-stone control**, which instanced billboards make awkward and real meshes may make easier: the wrong branch's stones should **crumble and drop away** as the player approaches, revealing the gap (currently they are simply absent from the moment the fork is built). Worth checking whether the stone representation chosen here makes that cheap.

### Full integration: from five prototypes to one app (roadmap, agreed 2026-08-23)

- **Status**: Roadmap agreed. **Stage A1 (scaffold), A2 (extract the game) and A3 (port the lobby) are done and verified end to end across two real browser sessions and the real Supabase project.** Target is a **demo round**: students join a lobby, get assigned to a team, one is the guide, the team plays a real round of Sky Path together, and it can be played again with a different guide. That demo round now works.

#### The diagnosis: nobody owns a round

All five build-sequence steps have a working proof, but they are five separate static pages joined by a query string. The single line that defines the current ceiling is in [lobby-prototype/lobby.js](lobby-prototype/lobby.js):

```js
const url = `${SKY_PATH_BASE_URL}?forks=${forks}&role=${myRole}&room=${roomGroupId}`;
```

Sky Path is launched as a **new tab, stamped with its state at birth, that never talks back**. Every "known gap, deliberately deferred" recorded elsewhere in this file is a symptom of that one fact, not an independent bug:

| Deferred gap | Why it's actually the same problem |
|---|---|
| Guide can't rotate between rounds | Role is baked into a URL that has already been opened |
| "Again"/reset isn't networked | The game tab has no concept of a round ending for the room |
| Score never reaches the roster | The game tab has no identity store, no class id, no token |
| Guide disconnect unhandled | Nothing owns the round's lifecycle to notice or recover |

Fixing these four separately would be four hacks. They collapse into one fix: **make a round a real, owned, networked object**, which requires Sky Path to be a *component inside* the session rather than a *page launched from* it.

#### The target shape

One Vite app, one Supabase client, one session context. Sky Path stops reading `location.search` and stops importing Supabase — it goes back to being ignorant of the network, which is what makes it testable and what lets a second game mode (quiz) slot in beside it later.

```
SessionProvider   — device token, roster-backed identity, session presence channel
  └─ RoomProvider — room channel, round state machine, guide assignment
       └─ <SkyPath forks role onForkChoice onRoundEnd />   (options in, callbacks out)
```

Aroha's device (guide, which never touched a button) advanced identically from the same relayed message. Both were pumped forward and arrived at fork 2 independently, in lockstep, with matching `forkIndex`, `sunP`, and `correctCount` — this is the anti-divergence property the whole "let the relay be the arbiter" design depends on, now observed rather than assumed. **Still not tested: genuine *simultaneous* taps from two players at once** (this test was one player tapping once) — the TODO's original caveat about needing that specific test stands; what's now confirmed is that the single-tap relay round-trip and role-split work correctly, which the concurrent case builds on.

**A real bug found and fixed by porting to React — stale/duplicate presence entries.** `lobby-room` is a public channel on the real shared Supabase project (already known — see the step-3 note below about "Bob, Jill, Jim" wandering in from other sessions). Supabase presence's `presenceState()` maps a key to an *array* of metas, and that array can transiently hold more than one entry per key during a reconnect (a dropped socket's old presence hasn't timed out when a new one for the same token joins) — the standalone prototype's plain `Object.values(state).flat()` silently rendered duplicate `<li>`s for this with no error, since vanilla DOM doesn't validate list identity. React does, and immediately surfaced it as "Encountered two children with the same key." Fixed by taking the newest meta per presence key, **and** de-duplicating by the payload's own `token` field as a second pass, since a stale session from a different origin/port hitting the same public channel can in principle carry a presence key that doesn't match its own tracked token (observed live: three duplicate "Jill" rows collapsed to one after the fix, using real leftover data from earlier testing today, not synthetic input). This is a genuine reliability fix for the "reconnecting students on school wifi" case the handoff calls out, not just a React-specific workaround.

**Two testing-environment traps hit and resolved, recorded so they aren't re-debugged as app bugs:**
  - **Multiple browser tabs share one origin's localStorage.** Simulating a second "device" by opening a second tab does *not* give it a separate identity token — both tabs' `getOrCreateToken()` read the same stored value until one explicitly clears it (the "New device" button). Reloading a tab that hasn't reset first silently adopts whatever token the *other* simulated device most recently wrote — this cost real debugging time before being recognized (a tab reporting "Guide view" incorrectly on both devices turned out to be exactly this, compounded by an in-flight code edit forcing an unrelated tab's HMR reload at the wrong moment). Only ever compare identities via a value read fresh from the page after the "New device" click, never assume a tab's identity is stable across a reload during multi-tab testing.
  - **A stale UI element reference silently degrades to a non-React-aware DOM write.** Using a `form_input`-style ref obtained *before* a page reload, without re-reading the page after, produced a case where the input's raw DOM `.value` was set correctly but React's controlled `useState` never saw the change — `join('')` fired with an empty name and no error anywhere. The fix is procedural, not a code fix: always re-fetch element references after any reload before driving them.

#### Decision: a player taps, the guide cannot (agreed 2026-08-23)

Supersedes the current prototype, where only the guide's client shows the left/right buttons. The pedagogy in the handoff is that the guide *speaks* the correct minimal pair aloud, face to face, and a **player** acts on what they heard. With the guide tapping, the guide's speech is decorative and the demo doesn't show the game. So: players see and press the buttons; the guide's client shows the safe/hazard markers and no buttons at all — the exact inverse of today.

- **Consequence — simultaneous taps need arbitration.** Several players can tap at once, and the two obvious client-side fixes both fail: acting optimistically on your own tap diverges from what others see, and "first message wins by arrival order" diverges too, because arrival order differs per client.
- **Intended solution — let the relay be the arbiter.** Supabase broadcast is relayed through one server that serialises messages, so *every* subscriber observes the same order. If no client ever acts on its own tap directly, and instead every client (sender included, via `config: { broadcast: { self: true } }`) acts only on messages received back from the channel, accepting only the **first** `fork-choice` seen for a given `forkIndex` and ignoring later ones, then all clients converge with no host, no election and no server code. Costs one round trip of latency on the tap, which is the right trade for a turn-based game.
- **Partially verified — see A3 below.** This design is now actually built (in `app/src/lobby/useLobby.js`, not just sketched) and the *single-tap* round trip was confirmed against the real Supabase project: a player's own device only advanced after its tap came back through the relay, and a second, non-tapping device (the guide) advanced identically from the same broadcast, with both landing on matching state. What that test did **not** exercise is the actual point of contention this design is for — two players tapping at, or near, the same instant. **Still needs a deliberate two-device simultaneous-tap test before this is trusted under real classroom conditions**; the fallback if ordering doesn't hold is to nominate the guide's client as round host (players send `fork-request`, host broadcasts authoritative `fork-resolved`) — more machinery, needs host migration on disconnect, but unambiguous.

#### Decision: consolidate first (agreed 2026-08-23)

Stage A before Stage D, rather than bolting a two-way channel onto the existing separate-page Sky Path to reach a demo sooner. Slowest route to something visible — the extraction of `main.js` has no user-visible payoff at all — but every later stage becomes cheap and nothing built gets thrown away. Chosen explicitly on "done right, not quickly." `prototype-threejs/` and the other prototype folders stay in place as reference until Stage A's acceptance test passes, then get removed.

### Agreed design, not yet built: fixed per-round seating chart, replacing live per-frame relayout entirely
- **Status**: Design agreed 2026-09-12, superseding the "pre-calculated inbound layout" idea directly above (kept struck through, not deleted, since the reasoning about *why* teammates need to become visible once you're past your own fog still holds — only the layout mechanics change). **Supersedes/resolves two specific risks flagged in that entry**: the "provisional/inbound occupant" bucket and its retraction-on-failure case are no longer needed at all — see below.
- **The core change**: today's layout (`layoutIslandGroup`/`repositionIslandOccupants`, called every frame from `relayoutAllIslands()`) recomputes who stands where from scratch, every frame, based on whoever *currently* happens to be resting at an island. Luke's simplification: compute each player's own seating assignment **once**, at round start, from the full group roster — self always centre, everyone else sorted (same deterministic token-sort already used) and assigned alternating sides/ranks exactly as today's algorithm does, but **only once**, then reused unchanged, at every island, for the rest of the round. A teammate's rank and side relative to *me* never changes once assigned, regardless of who has arrived, fallen, or not yet reached that island.
- **No compaction, ever — gaps are permanent and meaningful.** Worked example from Luke: player C (self, always centre) has A and B fixed to their left, D and E fixed to their right. Arriving at an island last, C sees A, B, D, E already standing in exactly those fixed spots, with only the centre gap (themselves) to fill. If D has already fallen by then, C sees *two* gaps: the centre (not yet filled by C) and D's fixed slot on the right (between the empty centre and E) — permanently empty for the rest of the round, not closed up. Carried to its conclusion: by the final island, only one teammate might remain, and they keep whatever fixed rank they were always assigned — which could easily be the outermost ("far left" or "far right") slot, since nothing here ever re-centres around whoever's actually present.
- **Why this is a strict simplification, not just a different feature**: no per-frame recomputation, no reshuffle/pop risk when someone arrives (nothing to reshuffle — the slot was always theirs), and it directly resolves the two open risks in the entry above: an inbound-but-not-yet-arrived teammate has nothing "provisional" to reserve (their slot was fixed from round start regardless of presence), and a teammate who falls before arriving simply never fills a slot that was never going to move anyway — no retraction logic needed. This is very likely also a meaningful simplification toward fixing the still-unverified guide/teammate-visibility system above: a static per-round lookup is far less likely to have the kind of subtle live-state bug a frame-by-frame Map-iteration-order system invites.

Luke's new instruction: **it should no longer be the guide's view at all.** A fallen player already has their own fixed personal seating chart (they were a full participant right up until they fell) — Watch mode should keep using exactly that, just with their own centre slot now permanently empty (they fell, so there's nothing to draw there — consistent with the no-compaction rule above, not a special case), and their camera switching from player-controlled to automatic, following whichever teammate is currently the last to move — the same *behaviour* the guide's camera already has, but driven through the fallen player's own existing per-round layout rather than a shared guide state machine. **The true guide is a separate case and is not stated to change** — the guide has no personal slot of its own (never a team member), so it's assumed to keep its current camera/arrangement unless Luke says otherwise.
