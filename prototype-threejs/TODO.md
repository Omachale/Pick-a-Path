### Path generation: build one fork at a time (anti-cheat)
- **Status**: ✓ Complete
- **Why (the real reason)**: this was previously filed as a memory/replay cleanup, but the actual motivation is **fairness**. Because only the *correct* branch of a fork feeds the cursor the next fork is planted from, the world-position of a downstream fork's pillars encodes which side was correct upstream of it. With the whole route present from the start, a player could read the shape of the path, the angle it takes toward the temple, and where distant pillars sit, and back-solve the current fork without needing the guide's clue at all. Building on demand means that information doesn't exist yet to be read.
- **The invariant**: at the moment any fork is being decided, no geometry beyond that fork's own two branches exists. Verified numerically — at fork N, exactly N sections exist, for all N in 1..6.
- **What changed**: `buildJourney()`'s single `for (k = 1..N_FORKS)` loop was split into `buildFork(k)` (pillars + both branches + curtain, planted at the current cursor) and `extendPastFork(k)` (the trunk beyond it, or the final approach, then `buildFork(k+1)`). The loop's locals `cursor`/`phase` became module state `journeyCursor`/`journeyPhase`, since the loop is now spread across choices rather than running in one pass. `buildJourney()` now lays only the intro trunk + fork 1; `choose()` calls `extendPastFork(forkIndex)` on a correct pick, before it reads `sec.trunkAfter`/`sec.approach` (which is what fills them in). A wrong pick builds nothing.
- **Why building at choice-time is safe** (rather than partway through the walk, as first sketched): the new geometry lands well beyond the current fork's curtain, and that curtain hasn't begun dissolving yet — `updateCurtains()` only trips `opening` once the walker is within `CURTAIN_OPEN_LEAD` (1.6) of it, and the curtain sits `CURTAIN_DIST` (~1.84) past the fork, so at choice-time the walker is still ~0.24 units short of the trigger. It's hidden from the moment it exists, with none of the mid-walk state machine deferring would need. Confirmed by eye in player view: the fog curtain fully masks where the path stops.
- **Ordering is byte-identical** for a full correct run: the sequence of `scatterAlong` calls is still intro → f1-left → f1-right → trunk1 → f2-left → f2-right → trunk2 → …, so the stone-variant round-robin and curtain/pillar array order are unchanged. Only forks never reached go unbuilt.
- **Files**: [src/main.js](src/main.js) — journey section header rewritten to document the invariant; `templeHeading()`, `buildFork()`, `extendPastFork()`, rewritten `buildJourney()`; `journeyCursor`/`journeyPhase` module state; `choose()` calls `extendPastFork()`; stale "whole route built up front" comments at the top of the file corrected.

### Path centring: aim the heading correction at the temple, not at zero
- **Status**: ✓ Complete
- **What**: `HEADING_CORRECTION` used to straighten the post-branch heading toward world heading **0** (`heading * (1 - HEADING_CORRECTION)`). That fixes the *direction of travel* but is blind to lateral drift already accumulated, so a run of same-side correct picks left the walker tracking parallel to the temple's centreline rather than converging on it — arriving noticeably off to one side. It now lerps toward `templeHeading(end)`, the heading that points from the branch's end straight at the temple at (0, −`TEMPLE_DISTANCE`). This straightens *and* re-centres in one step and needs no separate drift term: the further off-centre the cursor is, the more that heading differs from straight-ahead, so the pull scales itself. `HEADING_CORRECTION` keeps the same 0..1 meaning and the same 0.7 value.
- **Measured** (final walker x; temple centre is x=0, half-width ≈21.5):

  | Route | Before | After |
  |---|---|---|
  | All-left (`?forks=LLLLLL`) | −10.25 | **−3.79** |
  | All-right (`?forks=RRRRRR`) | +10.25 | **+3.79** |
  | Mixed | −0.16 | +1.33 |

  Worst case improves from 48% of the way to the temple's edge to 18% — comfortably central. The mixed case moves slightly the other way but both values are negligible; mixed routes self-cancel anyway, and the fix targets the pathological same-side runs.
- **Files**: [src/main.js](src/main.js) — `templeHeading()`, used in `buildFork()`; `HEADING_CORRECTION`'s comment updated to the new meaning.
- **Testing**: a pure-JS replay of the route geometry under both schemes reproduced the live game's measured −3.79 for all-left exactly, confirming the model is faithful before comparing the two.

### WebGL context creation failure on some browsers/GPUs
- **Status**: ✓ Mitigated (root cause is environmental, not fixable in this code)
- **What**: The game got stuck on the loading spinner forever in the user's own browser (Firefox on Windows), with console errors `WebGL creation failed: * tryANGLE (FEATURE_FAILURE_EGL_NO_CONFIG) * Exhausted GL driver options. (FEATURE_FAILURE_WEBGL_EXHAUSTED_DRIVERS)`. This is Firefox's ANGLE layer trying every backend it knows for that GPU and failing to get a context at all — a driver/GPU/browser-combination problem, not something wrong in the game's code. It didn't reproduce in the dev preview browser (different GPU/driver stack).
- **What changed**: `new THREE.WebGLRenderer(...)` was a single call with `{ antialias: true, powerPreference: 'high-performance' }` — the `high-performance` hint forces the discrete GPU on hybrid-graphics laptops, which is often exactly the GPU a blocklisted driver combination fails on. Renderer creation now retries with progressively safer options (drop `powerPreference`, then drop `antialias`, then accept `failIfMajorPerformanceCaveat: false` as a last resort) before giving up. If every attempt still fails, the loading spinner is replaced with an actual on-screen message (enable hardware acceleration / update GPU drivers / try Chrome or Edge) instead of hanging silently forever — that part is guaranteed to help regardless of whether the retries themselves fix any particular machine.
- **Files**: [src/main.js](src/main.js) — `createRenderer()` helper wrapping the `WebGLRenderer` construction in a `try/catch` retry loop, right after the `renderer / scene` section header.
- **Caveat**: this cannot be verified from here — the dev preview's GPU/driver stack doesn't reproduce the failure, so there's no way to confirm the retries actually help on the affected machine, only that they don't break the working case (confirmed: preview still loads and reaches fork 1 normally). If it still fails after this, the next step is the browser's own hardware-acceleration/GPU settings, not more code changes.

### Wrong-turn falling: Rapier gravity fall, wind, and camera follow
- **Status**: ✓ Complete
- **What**: Wired Rapier into main.js for the first time (previously only in blow-trial.js). When a wrong turn is confirmed, the character hands off from the normal walk-cycle to a free-falling rigid body — real gravity, a one-off randomized stumble, then a short decaying/rotating "wind" push (a single off-centre force that fades over `WIND_DURATION` while its horizontal direction sweeps around at `WIND_ANGULAR_SPEED`) — a cheap fake for a true helical field that reads as "caught by a gust and spun" without simulating a rotating force field. The placeholder red flash on a wrong turn has been removed entirely (function, DOM element, and CSS all deleted) — the fall itself is now the only wrong-turn feedback.
- **Camera** (reworked after first pass didn't actually clear the walkway): eases to a *fixed point beside the edge* — computed once in `startFall()` from the walker's position when the stub ran out, offset sideways by `FALL_CAM_SIDE` (2.8, more than the path's own half-width of 1.3, so the walkway's stones aren't between the camera and the open air below) and up by `FALL_CAM_HEIGHT`. - **More twist**: angular damping dropped from 0.3 to 0.15, the initial random stumble's angular velocity raised from ±1.5 to ±2.4 rad/s per axis, wind strength from 1.6 to 2.4, and the wind's off-centre lever arm (`WIND_SPREAD_Y`) from 0.35x to 0.45x figure height — the card now visibly tumbles across all three axes instead of a fairly flat spin.

### Full integration: from five prototypes to one app (roadmap, agreed 2026-08-23)

- **Status**: Roadmap agreed. **Stage A1 (scaffold), A2 (extract the game) and A3 (port the lobby) are done and verified end to end across two real browser sessions and the real Supabase project.** Target is a **demo round**: students join a lobby, get assigned to a team, one is the guide, the team plays a real round of Sky Path together, and it can be played again with a different guide. That demo round now works.

#### The diagnosis: nobody owns a round

All five build-sequence steps have a working proof, but they are five separate static pages joined by a query string. The single line that defines the current ceiling is in [lobby-prototype/lobby.js](../lobby-prototype/lobby.js):

```js
const url = `${SKY_PATH_BASE_URL}?forks=${forks}&role=${myRole}&room=${roomGroupId}`;
```

Sky Path is launched as a **new tab, stamped with its state at birth, that never talks back**. Every "known gap, deliberately deferred" recorded elsewhere in this file is a symptom of that one fact, not an independent bug:

| Deferred gap | Why it's actually the same problem |
|---|---|
| Guide can't rotate between rounds | Role is baked into a URL that has already been opened |
| "Again"/reset isn't networked | The game tab has no concept of a round ending for the room |
| Score never reaches the roster | The game tab has no identity store, no class id, no token |
| Guide disconnect unhandled | Nothing owns the round's lifecycle to notice or recover |

Fixing these four separately would be four hacks. They collapse into one fix: **make a round a real, owned, networked object**, which requires Sky Path to be a *component inside* the session rather than a *page launched from* it.

#### The target shape

One Vite app, one Supabase client, one session context. Sky Path stops reading `location.search` and stops importing Supabase — it goes back to being ignorant of the network, which is what makes it testable and what lets a second game mode (quiz) slot in beside it later.

```
SessionProvider   — device token, roster-backed identity, session presence channel
  └─ RoomProvider — room channel, round state machine, guide assignment
       └─ <SkyPath forks role onForkChoice onRoundEnd />   (options in, callbacks out)
```

#### Stages

- **Stage A — Consolidate. No new features.** Single Vite project; React shell; one config via `import.meta.env` instead of three separate gitignored `config.js` copies. Extract [src/main.js](src/main.js) — 2,194 lines of module-scope script reading 222 lines of hand-written DOM by ID — into a `mount(container, opts) → { dispose() }` module. The Three.js canvas stays imperative; the surrounding chrome (buttons, hint text, character carousel) becomes React. **Acceptance: solo Sky Path plays identically to today, and the lobby prototype's behaviour is reproduced inside the new app.** Deliberately zero new capability — that is the point, and it is why this stage is the one most likely to be skipped and most costly to skip.
- **Stage B — Real sessions and join flow.** A `sessions` table (join code → class id → teacher id). Teacher signs in, picks a class, starts a session, gets a code + QR. Student opens `/join/ABC123`, resolves the class, picks their name from the roster via the already-proven [supabaseIdentityStore.js](../identity/supabaseIdentityStore.js), and falls back to the ephemeral local store if they aren't on the roster (the fallback the step-5 notes flag as designed-but-unwired). Presence channel becomes `session-<id>` rather than the hardcoded `lobby-room` — which also fixes the real bug observed during step-3 testing, where unrelated participants ("Bob", "Jill", "Jim") from outside the session appeared in the lobby, because every device everywhere shares one channel name.
- **Stage C — Teacher gating.** Group management renders only for the authed teacher client. Also fixes the known clobbering bug where the group-editor table rebuilds from scratch on every presence sync, discarding in-progress edits when anyone joins or leaves.
- **Stage D — Round lifecycle.** *The actual prize, and the demo round.* An explicit state machine on the room channel: `lobby → assigning → playing → results → lobby`. Guide becomes a property of the **round**, rotated round-robin so every student takes a turn — required by the handoff doc, implemented nowhere. Sky Path mounts on `playing` and unmounts on `results`; a fall or an arrival ends the round for the whole room together. **Acceptance: two rounds back to back, a different guide each time, nobody touches a URL.**
- **Stage E — Score flows home.** Round end emits `{token, points, items}` up to the session layer, which credits it via `identityStore.addScore()`. This is the points payload that build-sequence step 3 specified ("include a points payload in this trial ... to prove a room can report a score up through session to the participant record") and that was never actually built. **Acceptance: finish a round, see the score on the teacher's roster view, and have it survive a simulated new day.**
- **Stage F — Deploy and harden.** GitHub Pages build, QR generation, load-time budget measured on real phones, guide-disconnect handling, and the free-tier Supabase pause-after-a-week caveat.

The data model and Supabase wiring are **unchanged** from the standalone prototype — presence keyed by identity token, grouping as a broadcast `{token: groupId}` map applied locally by each device, one `room-<groupId>` channel per group — because that model was already proven with real concurrent devices; only the DOM manipulation became React state. Files: `identity.js` (the device token + local identity store as a module singleton, not React state — it belongs to the browser, not a component's lifecycle), `useLobby.js` (presence, grouping, room-channel lifecycle), `Lobby.jsx` + `GroupEditor.jsx` (presentational), `GameRoom.jsx` (wires a live round to the room channel). `App.jsx` now switches between `<Lobby>` and `<GameRoom>` based on whether a `game-started` broadcast has landed — the first real (if minimal) instance of the round having an owner, ahead of Stage D's full state machine.

**This is also where the "a player taps, the guide cannot" decision below got its first real implementation**, not just a design. `useLobby`'s room channel is created with `broadcast: { self: true }`, and exposes `sendForkChoice`/`onForkChoiceReceived` rather than ever calling `applyChoice` from a local tap — every device, sender included, only acts on the copy the relay sends back. Both `fork-choice` and `game-started` handlers are registered *before* `.subscribe()` (not after — adding `.on()` post-subscribe isn't something supabase-js documents as supported).

**Verified with two real, independently-identified browser sessions against the live Supabase project** (not a mock, not a single-device simulation): "Kahu" and "Aroha" joined the real `lobby-room` presence channel under distinct tokens, were grouped into `Group 5` via the broadcast-and-apply flow (confirmed independently on both sides), auto-joined `room-5`, and one device's "Start Sky Path" click produced a `game-started` broadcast that assigned **guide to Aroha and player to Kahu on both devices independently** — no shared state, no coordinator, just each client comparing the broadcast `guideToken` to its own token. Kahu's device (player) correctly showed the fork buttons with the hint "you cannot see which way is safe"; Aroha's device (guide) showed the safe/hazard markers with buttons hidden entirely.

**The core mechanic — the relay as arbiter — worked exactly as designed on the first real cross-device test.** Kahu (player) tapped `right` (the correct side, confirmed from the guide's own view first). That tap went out as a `fork-choice` broadcast and came back through Supabase's relay to *both* devices; neither device ever applied the tap locally. Kahu's own device only advanced (`correctCount: 1`, `walking: true`) once the broadcast returned — proving the "not even the sender applies its own tap directly" design actually holds, not just in theory. Aroha's device (guide, which never touched a button) advanced identically from the same relayed message. Both were pumped forward and arrived at fork 2 independently, in lockstep, with matching `forkIndex`, `sunP`, and `correctCount` — this is the anti-divergence property the whole "let the relay be the arbiter" design depends on, now observed rather than assumed. **Still not tested: genuine *simultaneous* taps from two players at once** (this test was one player tapping once) — the TODO's original caveat about needing that specific test stands; what's now confirmed is that the single-tap relay round-trip and role-split work correctly, which the concurrent case builds on.

**A real bug found and fixed by porting to React — stale/duplicate presence entries.** `lobby-room` is a public channel on the real shared Supabase project (already known — see the step-3 note below about "Bob, Jill, Jim" wandering in from other sessions). Supabase presence's `presenceState()` maps a key to an *array* of metas, and that array can transiently hold more than one entry per key during a reconnect (a dropped socket's old presence hasn't timed out when a new one for the same token joins) — the standalone prototype's plain `Object.values(state).flat()` silently rendered duplicate `<li>`s for this with no error, since vanilla DOM doesn't validate list identity. React does, and immediately surfaced it as "Encountered two children with the same key." Fixed by taking the newest meta per presence key, **and** de-duplicating by the payload's own `token` field as a second pass, since a stale session from a different origin/port hitting the same public channel can in principle carry a presence key that doesn't match its own tracked token (observed live: three duplicate "Jill" rows collapsed to one after the fix, using real leftover data from earlier testing today, not synthetic input). This is a genuine reliability fix for the "reconnecting students on school wifi" case the handoff calls out, not just a React-specific workaround.

**Two testing-environment traps hit and resolved, recorded so they aren't re-debugged as app bugs:**
  - **Multiple browser tabs share one origin's localStorage.** Simulating a second "device" by opening a second tab does *not* give it a separate identity token — both tabs' `getOrCreateToken()` read the same stored value until one explicitly clears it (the "New device" button). Reloading a tab that hasn't reset first silently adopts whatever token the *other* simulated device most recently wrote — this cost real debugging time before being recognized (a tab reporting "Guide view" incorrectly on both devices turned out to be exactly this, compounded by an in-flight code edit forcing an unrelated tab's HMR reload at the wrong moment). Only ever compare identities via a value read fresh from the page after the "New device" click, never assume a tab's identity is stable across a reload during multi-tab testing.
  - **A stale UI element reference silently degrades to a non-React-aware DOM write.** Using a `form_input`-style ref obtained *before* a page reload, without re-reading the page after, produced a case where the input's raw DOM `.value` was set correctly but React's controlled `useState` never saw the change — `join('')` fired with an empty name and no error anywhere. The fix is procedural, not a code fix: always re-fetch element references after any reload before driving them.

#### Decision: a player taps, the guide cannot (agreed 2026-08-23)

Supersedes the current prototype, where only the guide's client shows the left/right buttons. The pedagogy in the handoff is that the guide *speaks* the correct minimal pair aloud, face to face, and a **player** acts on what they heard. With the guide tapping, the guide's speech is decorative and the demo doesn't show the game. So: players see and press the buttons; the guide's client shows the safe/hazard markers and no buttons at all — the exact inverse of today.

- **Consequence — simultaneous taps need arbitration.** Several players can tap at once, and the two obvious client-side fixes both fail: acting optimistically on your own tap diverges from what others see, and "first message wins by arrival order" diverges too, because arrival order differs per client.
- **Intended solution — let the relay be the arbiter.** Supabase broadcast is relayed through one server that serialises messages, so *every* subscriber observes the same order. If no client ever acts on its own tap directly, and instead every client (sender included, via `config: { broadcast: { self: true } }`) acts only on messages received back from the channel, accepting only the **first** `fork-choice` seen for a given `forkIndex` and ignoring later ones, then all clients converge with no host, no election and no server code. Costs one round trip of latency on the tap, which is the right trade for a turn-based game.
- **Partially verified — see A3 below.** This design is now actually built (in `app/src/lobby/useLobby.js`, not just sketched) and the *single-tap* round trip was confirmed against the real Supabase project: a player's own device only advanced after its tap came back through the relay, and a second, non-tapping device (the guide) advanced identically from the same broadcast, with both landing on matching state. What that test did **not** exercise is the actual point of contention this design is for — two players tapping at, or near, the same instant. **Still needs a deliberate two-device simultaneous-tap test before this is trusted under real classroom conditions**; the fallback if ordering doesn't hold is to nominate the guide's client as round host (players send `fork-request`, host broadcasts authoritative `fork-resolved`) — more machinery, needs host migration on disconnect, but unambiguous.

#### Decision: consolidate first (agreed 2026-08-23)

Stage A before Stage D, rather than bolting a two-way channel onto the existing separate-page Sky Path to reach a demo sooner. Slowest route to something visible — the extraction of `main.js` has no user-visible payoff at all — but every later stage becomes cheap and nothing built gets thrown away. Chosen explicitly on "done right, not quickly." `prototype-threejs/` and the other prototype folders stay in place as reference until Stage A's acceptance test passes, then get removed.

### Multiplayer: participant identity must be designed roster-ready from the start
- **Status**: All five build-sequence steps now have a working proof — identity, Supabase relay, live participant sync, grouping, the real Sky Path game running networked per room, and now persistent classes with a real teacher account and roster (see below). What's left is turning these five separate prototypes into one real app: a React lobby UI, teacher-role gating, a proper join-by-QR flow, and wiring the roster-backed identity store into the actual multi-device lobby (proven standalone, not yet integrated with lobby-prototype's group/room flow).
- **Why this is here**: the original brief called for points/rewards that persist across game modes within a lesson, and scores/equipment that persist across days so a student can log back in as the same character. That requirement had fallen out of scope while the diorama/graphics work was underway and was restored on 2026-08-23 — see [ESL-classroom-game-HANDOFF.md](../ESL-classroom-game-HANDOFF.md) ("Persistent classes, scores & equipment" section) for the full reasoning. Recording it here too so it isn't lost a second time.
- **What this changes**: not the architecture (the two-layer session/game-mode split and "identity keyed by stable token, not connection" rule already anticipated this) — it changes **sequencing**. Specifically:
  - **Score and inventory must live on the participant's identity, not on the room.** A room (a Sky Path run, a quiz round) reports results up to the session layer as "this participant earned N points / item X this round"; the session layer is what credits it to the participant record. No game mode should accumulate or read a running total itself.
  - **Equipment** (cosmetic/functional items a character accumulates, e.g. rewards from Sky Path) is a column on the same roster row as score — same shape, no separate model, but worth a schema slot from day one rather than retrofitting once score is already a bare integer.
  - **The participant identity model (build-sequence step 1, not yet started) must be designed as an opaque stable token whose lookup (token → display name/score/equipment) goes through one layer** — backed by local-only state initially, swapped for a real Supabase roster row once teacher accounts/roster CRUD are built (step 5). The lobby and game-mode code should not need to change when that swap happens.
  - **Whole-class shared-screen pattern** (a prompt shown on the projected main screen while students answer privately on their own phones — e.g. a quiz round) is confirmed as a variant of the existing whole-class mode (lobby without grouping = one room containing everyone), not a new architectural case. The projector client already renders room state; this just means a game mode can also target the projector as a display surface, not only the phones.
- **Not yet started, but not blocking Sky Path polish**: none of this needs building before further single-player Sky Path work continues — it's the shape the *next* phase (lobby + multiplayer relay) needs to be built in from the outset.
